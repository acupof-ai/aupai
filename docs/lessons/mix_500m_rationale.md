# 500M 的配比：让组成跟着目标，而不是跟着仓库

**这一版和上一版最大的差别不是任何一个权重，是权重的来源。**

`mix_30b_stage2.json` 里 code 拿到 29.33%，因为 RedPajama github 有 7.57B
token 摆在那里。今天量出来那 7.57B 里只有 **0.42B 能过 `ast.parse`**——
3,747,157 行里 209,668 行是 Python。**那个 29.33% 从来不是一个关于目标的
判断，它是一个关于库存的判断，而库存本身是错的。**

用户点名的就是这件事。所以这份配比里，权重先由能力目标定，供给只作为一个
**能否决权重、但不能设定权重**的约束出现。

## 1. 配比

生成器 `scripts/write_mix_500m.py`（`--selftest` 10/10），文件
`data/mix_500m.json`。总预算 20B，理由在 §2.2。

| 域 | 权重 | 要 | 一轮供给 | 轮数 | 为什么是这个数 |
|---|---|---|---|---|---|
| **code（合计）** | **34.511%** | 6.90B | 9.27B | **0.74** | 目标是代码模型，所以它是最大的一根 |
| └ code_py_starcoder | 32.945% | 6.59B | 8.85B | 0.74 | 按供给比例分，两边同轮数 |
| └ code_py_rp1t | 1.566% | 0.31B | 0.42B | 0.74 | 已过 ast.parse 的那 209,668 行 |
| math_owm_stage2 | 26.390% | 5.28B | 6.51B | 0.81 | 与 code 共享符号结构，这个尺寸还吃得下 |
| en_c4_stage2 | 16.240% | 3.25B | 2.40B | 1.35 | docstring 和题面是英文；低于 ~15% 散文侧先于代码侧退化 |
| textbook_30b | 10.150% | 2.03B | 1.61B | 1.26 | Phi-1 的"教科书质量"那一根；拿到 cot 让出的一点 |
| cot | 8.120% | 1.62B | 0.42B | 3.83 | 供给最小，8% 是**上限**不是目标——见 2.1 |
| chatml | **0.780%** | 0.156B | 0.0390B | **4.00** | **不是选的，是算的**——见 §5.2 |
| chat_qa | **0.764%** | 0.153B | 0.0382B | **4.00** | 同上，同一批行的另一种渲染 |
| zh_web | 3.045% | 0.61B | 21.29B | 0.03 | 目标是英文代码模型 |

**表里的权重是生成器输出的，不是我写进去的。** 目标域的权重由 `OBJECTIVE`
声明，两个 supply-capped 域的权重由 `_ceiling_weight` 从供给推出来，代码里
写的是 `None`——**一个供给上限不是判断，是算术，不该有第二份手抄本**（§5.2）。
九个域的行数精确加总到 4,882,812。

**code 是一个目标，摊在两份语料上。** 目标说的是"34.51% Python"，不是
"34.51% starcoder"；两份之间怎么分是一个供给事实，所以它在拆分函数里，不在
目标表里。`code_rp1t` 里过了 `ast.parse` 的 209,668 行（420,646,182 token）
是我们已经付过一遍全量扫描才确认的，和 starcoder 是同一种数据——丢掉它等于
白扔 code 域 4.5% 的一轮供给（fb 指出）。

**按供给比例分，是唯一让两边轮数相等的分法**（都是 0.74）。没有证据说哪一份
per-token 更好，所以没有理由多读其中一份；任何别的比例都是一个没测过的质量
断言。**保持两个域而不合成一个**，因为来源和过滤都不同（starcoder 已去重且
质量过滤，rp1t_python 是我们自己的 ast.parse 一遍），合并会把两个指纹并成
一个，之后 per-role 读数就归因不到任何一边。

**目标声明的 34% 到了 mix 里是 34.51%**：两个 supply-capped 域吃到 1.54%，
剩下的按比例还给目标域（`_allocation`）。**让出来的权重是一个组成决定，不是
一个舍入决定**——不这么做，那 1.46pt 会消失在 largest-remainder 的余数里，
权重和悄悄变成 0.9852。

**zh_web 从 10.955% 降到 3% 是这次转向最干净的一个例子**：21.3B 的供给一夜
之间变得无关紧要，因为目标不再需要它。上一版里它拿 10.955% 的唯一理由就是
它多。

## 2. 两个我做了决定而不是继承的数

fb 点名要这两个由我决定。

### 2.1 每域轮数上限：cot 的 8% 是上限，不是目标

轮数上限是算出来的，不是敲进去的：`cap = ceil((used + want) / pool)`，
由脚本生成，永不手编。

**真正的决定发生在 cot 上。** 它的供给只有 0.424B（下表是生成器输出的
shipped 权重和抽取轮数，不是目标声明值——两者差一个 §1 的重归一化）：

| cot 目标权重 | shipped 权重 | 轮数 |
|---|---|---|
| 9% | 9.137% | **4.31**（越线） |
| 8% | 8.122% | 3.83 |

Muennighoff 的结果是 **≤4 轮几乎不要钱**（8.7B 模型 4 轮对单轮，最终验证
损失差 +0.5%，`ds.muennighoff_four_epoch`），过了 4 轮重复 token 开始不付账。

所以 9% 会让 cot **花钱买重读**——这是保留在 8% 的全部理由，**它是一个
供给论证，不是一个价值论证。**

**这里要撤回一句话，并且它是我自己写的规则的反例。** 初稿的理由是一句跨角色的
nat/B 比较——"同样的成本，某某倍的实测速率"。
**`docs/standards/training_loop.md` §6 明确禁止用 nat/B 做跨角色的资源分配**
——迁移会把每个角色的 nat/B 按一个未测且逐角色不同的幅度抬高，所以跨角色的
排序不能假定成立。**那一节是我写的，然后我在下一份文档里违反了它。**

§6 里已经记着同一句话："写下限制不等于遵守它"，起因是我在给出禁令的同一份
文档里走私了一次跨角色读法，由 44 审出。**今天这是第二次，同一条规则。**
一条规则被同一个人在两天内违反两次，说明它作为原则不起作用。

**所以它现在是一段代码，不是一条原则。** `_refuse_cross_role_rate` 在生成器
里对每一条权重理由跑一遍：一句话里出现两个角色名、并且引了 nat/B 数字，
生成器直接 `SystemExit`。自检第 8 条拿**真正被撤回的那句原文**做失败样本，
不是我编的一句。

**这道闸当场又抓到一条我没看见的。** 它第一版只匹配域名（`textbook_30b`），
而被撤回的那句写的是"textbook"——**守卫是照着违规写的，仍然没抓到违规，因为
违规是用人话写的而守卫在读标识符。** 改成匹配人话之后，`zh_web` 的理由也被
拦下了：那里写着"nat/B 是七个域里第三低的"——**一个跨角色的 nat/B 排名，和
被撤回的那句是同一件事，只是它伪装成了一句背景交代。** 一并撤回。

`cot` 的理由里现在不引那两个被撤回的数字，因为**这道闸分不清"引用"和
"引用来否定它"，而且它不该去分**——给"我是在否认它"开一个例外，就是下一次
违规要走的那个口子。

**8% 和 10% 都保留，但理由重写为：** cot 的 8% 是 4 轮线定出的**上限**；
让出的那一点给 textbook，因为**目标**把它排在下一位（Phi-1 点名"教科书
质量"这一类数据），不是因为它的 nat/B 更高。

生成器的自检对这条断言了两个方向：shipped 配置下没有任何域越线，**并且**
把 cot 调回 9% 时警告仍会响。**一个从未响过的上限，和一个响不了的上限，
分辨不出来。**

### 2.2 总预算：20B，不是继承的 30B

**这一节的论证被推翻过一次，而且是整条作废，不是改算术。**

初版写的是"非 zh_web 的一轮供给只有 15.45B，所以 20B"。starcoder 投影到
8.85B 之后，那个供给是 **20.30B**。fb 的裁定是重推，不是把 15.45 改成 20.30
再保留句式——**因为改数字会留下一个读起来仍像供给论证的段落，而供给已经不再
是那个理由了。** 下面把死掉的部分划掉，再给活着的部分。

#### 划掉的两条

- ~~"一轮供给只有 15.45B，所以 20B"~~ ——供给是 20.30B，**这条死了**。
- ~~"20B 是没有任何域越 4 轮线的最大预算"~~ ——**循环**。20B 时唯一越线的
  候选是 cot，而 cot 的 8% 本身就是被 4 轮线定出来的（§2.1）。用一个由预算
  定出的权重去定预算，不是判据，是不动点。

第二条尤其要划掉而不是修补：它在今天的数字下**仍然是真的**，只是它什么也没
说明。一个恰好为真的循环论证，比一个明显错的论证更难被下一个人发现。

#### 约束：供给能否掉 20B，不能选中 20B

这是一个**界**，不是**理由**。每个域在它的 shipped 权重下读到 1 轮所对应的
总预算（数字由生成器输出重算，不是从上一版抄的）：

| 域 | 一轮供给 | 权重 | 开始重复的预算 |
|---|---|---|---|
| chatml | 0.0390B | 0.780% | **5.00B** |
| chat_qa | 0.0382B | 0.764% | **5.00B** |
| cot | 0.424B | 8.120% | **5.22B** |
| en_c4_stage2 | 2.404B | 16.240% | **14.80B** |
| textbook_30b | 1.610B | 10.150% | 15.86B |
| math_owm_stage2 | 6.513B | 26.390% | 24.68B |
| code（合计） | 9.271B | 34.511% | 26.86B |
| zh_web | 21.293B | 3.045% | 699.28B |

三个小域允许按 Muennighoff 的 ≤4 轮，那么**第一个真正吃紧的是 en_c4，在
14.8B**；20B 时它 1.35 轮，已在重复但远在 4 轮线内。**供给对 20B 的判决是
"可以"，不是"必须"。** 这一节到此为止——它划出一个区间，选点是下一节的事。

#### 理由：吞吐，不是供给

**20B 和 30B 的差是 0.058 nat（Chinchilla，N=493.6M：2.6761 对 2.6185），
代价是八张卡上多 12 小时**（30K tok/s/GPU 假设下 23.1h 对 34.7h；七张卡是
26.5h 对 39.7h；tilerl 在测真吞吐）。

这个交换在别的时候可能划算，**在这一个 run 上不划算，因为这个 run 的产出不是
那 0.058 nat**。形状（d1024/L32 + AttnRes）、优化器缩放规则（Muon，depth-muP
的两条前提在这里都不成立）、语料（组成第一次跟着目标走）——**三处同时首次
启用，没有一处有先例读数。** 这种 run 的价值在于**它多快能告诉你哪里错了**，
而不是它最终损失多低。多花 50% 的墙钟去买 2% 的损失改善，买的是错误配置也
一样能拿到的那部分。

**所以 20B 是被选出来的，不是被逼出来的**，而这正是需要写明的地方：供给
多出 5B 之后，不抬预算是一个判断。fb 的提醒对——**多出来的 token 不等于有用
的 token，因为拿到更多供给就默认抬预算，正是上一版配比跟着库存走的那个机制**，
只是换了个方向。

#### 什么会让它动

- **tilerl 实测吞吐远好于 30K tok/s/GPU**：12 小时的差价缩小，主理由变弱。
- **shakedown 干净地跑完**："三处都没有先例"不再成立，主理由变弱。
- **en_c4 供给显著增加**：14.8B 那个界上移——但那只放宽约束，不构成抬预算的
  理由（这正是上面划掉第一条的原因）。

## 3. code 的权重是一个函数，不是一个常数

`--code-tokens` 是生成器的参数，传的是 **starcoder 的量**，rp1t 那 0.421B
由脚本自动加上。**code 合计权重固定在 34.51%（那是目标），轮数随供给浮动**：

| starcoder | code 总供给 | 轮数 | cap | starcoder / rp1t 权重 |
|---|---|---|---|---|
| 3.0B | 3.42B | 2.02 | 3 | 30.268% / 4.244% |
| 6.0B | 6.42B | 1.08 | 2 | 32.251% / 2.261% |
| **8.85B（当前投影）** | **9.27B** | **0.74** | **1** | **32.945% / 1.566%** |
| 12.0B | 12.42B | 0.56 | 1 | 33.343% / 1.169% |

**合计不动，只有两份之间的劈分动**——按供给比例分是唯一让两边轮数相等的
分法，所以 starcoder 越多，它在 code 里占的比例越高。自检第 1 条对着三个
不同供给断言合计行数不变。

**8.85B 是投影不是实测**：3b 从稳定的 ~148.8M/分片外推 59 分片，已确认无
漂移。全部写完后按实测终值重跑 `--code-tokens`，这张表定死一行。

**低于 2.5B（总供给，不是 starcoder 单独）生成器直接拒绝**，并且拒绝信息里
写明**降权重是错误的修法**：一个代码优先的目标，如果只能靠把同一批代码读
四遍来供养，那是另一个实验。要么降总预算，要么提高供给，不要降那个权重——
**降权重就是让组成重新跟着供给走**。

## 4. Python only

`ast.parse` **同时是语言识别和语法过滤**——这是它比一个语言分类器好的地方：
一个不能解析的 Python 文件和一个非 Python 文件，对这个目标是同一件事。

先例是 Phi-1：**一种语言，6B 精选 Python token，1.3B 参数上 HumanEval 50.6**。
我们在 493.6M 上用 6.90B Python token，参数少 2.6 倍，token 多 15%。

样板率的测量支持同一个方向：code_rp1t **至少 7.49%** 的 token 落在跨 ≥3 篇
文档复现的文本里（en_c4 同一把尺子是 0.16%，47 倍），而且 **6.7% 的文档
超过一半是复现文本**。质量集中在少数文档，所以丢文档比做 span 级去重便宜
一个数量级。starcoder 的 Python 切片是已经过这道工序的，rp1t 不是。

## 5. ChatML 必须进预训练

语料里实际上没有 ChatML——**每个域都低于 0.075%**。

裁定（fb）是把现有的 `问：/答：` chat 域**渲染两遍，每种格式各一遍，落成两个
独立域**。不加新数据，一处 build 侧改动。两个域而不是一个混合域，是因为
**指纹不同，而且一种格式灵一种不灵时能读得出来**——合并就归因不到任何一边。

**理由不是"多样性好"，是 200M 那一轮的实测：SFT 只装被喂的范式。** 指望
SFT 教会 base 一个它从没见过的前缀，是这个项目已经输过一次的赌。

3b 已落地（2026-09-01）：新建 `data/corpus/chat_qa/` 和 `data/corpus/chatml/`，
`data/corpus/chat/` **原封未动**（chat_qa 是从它读出来另写的副本；保名保指纹，
六个 ladder mix 靠它）。两域各 160,414 篇，**train.py 口径的精确 token 数**：
chat_qa **38,187,650**、chatml **38,995,846**，ChatML markup 净增 808,196。
holdout 切片已冻结，0 held-out。口径这件事见 §5.3——它差点让两个域用两把尺子。

### 5.1 供给取错了域，而守卫看不见（3b 查出，2026-09-01）

**我把 `wiki_chat` 的 stamp（0.284B）当成了 chat 域的供给。** `wiki_chat` 是
wiki+chat 的**合并域**（12 shards），而 `问：/答：` 实际只在
`data/corpus/chat/`：**160,414 行 / 0.038B**（3b 实测）。**拿合并域的 stamp
代表它的一个子集，高估约 7 倍。**

**后果不是"数字错了"，是守卫静默：**

| 渲染源 | 一轮供给 | 3% 下的轮数 |
|---|---|---|
| chat-only（实测） | 0.038B | **15.79** |
| wiki_chat（我用的） | 0.284B | 2.11 |

生成器有 4 轮线警告，**它在 0.284B 下不响**。真值 0.038B 下实际是
**15.79 轮**——一个 0.038B 的语料读 16 遍，而上限一声不吭。**守卫没坏，
是喂给它的供给数从未为它命名的那个域测过。一个检查的真实性不超过它输入的真实性。**

这里还有一个我自己引入的算术错误要记：我在给 fb 的消息里写了 0.076B，那是
**两个域之和**，没有任何单个域装着它。裁定回来时变成"每域 ≤1.52%"——
**1.52% 在 0.038B 上是 8.00 轮，正好是上限的两倍。** 正确是每域 0.76%、
合计 1.52%。一个把两份加起来的数，套回到其中一份上，翻倍且看不出来。

### 5.2 一个 PASS，精度不足以支撑它

**这一条是上一条的同形复发，在同一个域上，同一天。**

按每域 0.76% 生成，chat_qa 抽到 **3.99996 轮**——过线，差 **10 万分之四**。
而供给是两位有效数字：0.038B 意味着 ±0.5M，**±1.3%**。取供给的下沿，同样
的权重是 **4.05 轮，越线**。

**守卫给了一个它的输入没有分辨率去支撑的判决。** 它没坏，也没被喂错域——
这次域是对的，**精度不对**。区别只在这里：wiki_chat 那次输入指向了错的东西，
这次输入指向对的东西但太粗，粗到判决在它自己的误差棒里翻面。**两次的表象
完全一样：一个安静的 PASS。**

所以生成器现在做两件事：

1. `SUPPLY_RELATIVE_ERROR` 记下哪些供给是有误差棒的，**4 轮线在整条带子上
   判**——点估计过线、下沿越线，一律报"这不是一个 PASS，是一个分辨不了的
   判决"，并说明修法是取精确值或降权重，不是接受它。
2. **两个 supply-capped 域的权重不再手写。** `OBJECTIVE` 里它们是 `None`，
   由 `_ceiling_weight` 从供给和 4 轮线现推。手写的 0.0076 就是这么坏的：
   它是照 38.0M 精确值算出来的，供给换成两位有效数字之后它没跟着变，
   **变成了一枚落对了面的硬币**。一个供给上限不是判断，是算术，
   **不该有第二份手抄本**。生成器对 `None` 有断言，写回数字会被拒。

最终权重：**chatml 0.780%、chat_qa 0.764%，各 3.9999 轮**——3b 已报出精确
整数，误差棒条目随之删空，权重自动回到**锐上限**，
`_ceiling_weight` 用满到最后一行（自检断言"再多一行就越线"）。**除了删那两条
条目，没有改任何别的地方**——这正是把权重做成推导而不是字面量买到的东西。

**`SUPPLY_RELATIVE_ERROR` 留着，空的。** 机制本身是唯一能让一个粗供给自己
说出"我判不了"的东西；下一个以两位有效数字到达的域需要它在到达时就在，
而不是在它已经发车之后。

自检第 9 条用**自己的 fixture** 断言：植回 2sf 的 38.0M，手写的 0.0076
在点估计上过、在误差带上不过，而推导出的权重两端都过。**不用 live 值**——
一个盯着 live 值的检查会在缺陷被修好的那一刻变红，那是在测缺陷不是测守卫。
第 7 条今天早些时候就是这个形状，已经改过一次。

`chatml` 是一个**新目录**，不写进任何 `data/mix_scale_*.json` 命名的目录
（chat / code / en / math / textbook / web_hq / wiki）。**`chat_qa` 这个名字
正是被这条闸逼出来的**：fb 的裁定说渲染成 `chat`，而六个 ladder mix 都点名
`data/corpus/chat/`（权重 0.011768）——**裁定和约束撞了，是守卫让人看见的**。

### 5.3 两个数，两把尺子

**同一个域，同一天，第三个缺陷，仍然在输入上。**

3b 报来的两个数：chat_qa **38,027,236**、chatml **38,995,846**。两个都是实测，
两个单独看都合理，而且它们**不是同一个量**——前者是裸 `len(ids)`，后者是
stamp。中间差一个 EOS。

`scripts/count_tokens.py:16`：

```python
CONVENTION = "ids + one <eos> per document (train.py encode)"
def count_docs(texts, tok):
    return sum(len(e.ids) + 1 for e in batch_fn(list(texts)))   # ← +1
```

**stamp 数的是 train.py 真正喂进去的那个数。** 而 mix 里其余七个域的供给
全部取自 stamp。拿裸 ids 当 chat_qa 的池子，就是**把一个域放到另一把尺子上**
——它的轮数会相对整个 mix 悄悄缩放。代价 157 行，方向是少读。

**怎么发现的：不是读出来的，是算出来的。** 3b 说那个 stamp（38,187,650）是
3 分片采样外推、让我别用。差值是：

```
38,187,650 − 38,027,236 = 160,414 = 文档数，每篇整 1 个 token
```

**一个按字节缩放的外推不可能正好落在"每篇差整 1"上。** 这个数字形状排除了
"采样噪声"这个解释，剩下的唯一解释就是 EOS。**一个可疑的数不需要相信或不
相信，它需要被算一遍。**

**顺带查出 stamp 自己的一处误标**：`_write_stats` 里 `n_sample = min(3,
len(shards))`，分片数 ≤3 时它读的是全部分片；但 `tokens_config` 那行字符串
无条件写着"N/M-shard sample extrapolated by bytes"。**一个把精确值标成估计的
字段，和把估计标成精确一样坏**——读的人要么去做一次不必要的重测，要么反过来
不信任一个本来可信的数。已发给 de 的 instruments 课题。

**我第一版守卫是编的，自检还过了。** 我想从两个供给本身检出这件事：如果
两个同源域的供给差正好是 n_docs，就说明一个少了 EOS。**这个规则不成立**
——实际差是"markup 增量 + 缺失的 EOS"，而 markup 增量事先不知道。它通过自检
只是因为**我挑的 fixture 正好符合我编的规则**。删掉了。

**留下的是一条更窄但真的守得住的**：`SUPPLY_UNITS` 要求每个供给声明自己的
单位，任何一个没声明、或声明成非 train.py 口径的，生成器直接拒绝。**它不能
识别一个标错的数字，我也不声称它能。** 它做的是让"这个数是什么单位"这个
问题在数字进入的那一刻无法跳过——而那正是 3b 那两个数会撞上的地方。

自检第 10 条断言三件事：shipped 那组过；删掉一个域的单位声明后拒绝；把一个
域标成 `bare ids` 后拒绝。外加一条：两个域的差必须是 markup 的 808,196 而
不是 n_docs 的 160,414，**差值一旦变回 160,414 就说明又有一个数是裸 ids**。

## 6. 每一个 epochs 值都是暂定的

**这一节不能被跳过。** 这些域都还没有 token cache，所以池子是从 stamp
估出来的：`stamp_tokens // (seq+1)` 再减 `n_val`。

**stamp 给的是 token，池子是打包后的行。** 两者差多少取决于文档长度分布，
而这正是 stage-2 那一版把 math_owm 的 cap 从 2 误标成 1 的地方。

**发车前每一个 epochs 都要对着它自己的 cache 重算。** JSON 里每条都带
`epochs_pool_source: "ESTIMATED from the stamp; no token cache exists yet"`，
不是脚注，是字段——**一个读起来像实测的暂定值，是这个仓库反复找到的那个缺陷。**

## 7. 作废条件

- **starcoder 落地量已知**：重跑 `--code-tokens <实测>`，§3 的表定死一行，
  两个 code 域的劈分随之变。
- **3b 报出 chatml/chat_qa 的精确 token 数**：从 `SUPPLY_RELATIVE_ERROR` 里
  删掉那两条，权重自动从误差带上限回到锐上限（§5.2）。**只删条目，不改权重**
  ——改权重就是又手抄一遍。
- **任何域建了 token cache**：§6 对该域失效，epochs 从估计变成实测。
- **tilerl 报出真吞吐**：§2.2 的 12 小时差价重算。远高于 30K tok/s/GPU 的话，
  20B 的主理由变弱，**但那时要重新论证，不是顺势抬到 30B**。
- **供给结构变化**（新的高质量域，或 starcoder 远超投影）：**§2.2 的约束界
  上移，理由不变**——供给放宽不构成抬预算的理由，这正是 §2.2 划掉第一条的
  原因。
- **目标变化**：整份文档作废。这是它和上一版最重要的区别——上一版的权重
  在目标变化时不会失效，因为它们本来就不是从目标推出来的。
