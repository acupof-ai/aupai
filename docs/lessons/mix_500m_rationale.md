# 500M 的配比：让组成跟着目标，而不是跟着仓库

**这一版和上一版最大的差别不是任何一个权重，是权重的来源。**

`mix_30b_stage2.json` 里 code 拿到 29.33%，因为 RedPajama github 有 7.57B
token 摆在那里。今天量出来那 7.57B 里只有 **0.42B 能过 `ast.parse`**——
3,747,157 行里 209,668 行是 Python。**那个 29.33% 从来不是一个关于目标的
判断，它是一个关于库存的判断，而库存本身是错的。**

用户点名的就是这件事。所以这份配比里，权重先由能力目标定，供给只作为一个
**能否决权重、但不能设定权重**的约束出现。

## 1. 配比

生成器 `scripts/write_mix_500m.py`（`--selftest` 6/6），文件
`data/mix_500m.json`。总预算 20B，理由在 §2.2。

| 域 | 权重 | 要 | 一轮供给 | 轮数 | 为什么是这个数 |
|---|---|---|---|---|---|
| **code（合计）** | **34%** | 6.80B | 9.27B | **0.73** | 目标是代码模型，所以它是最大的一根 |
| └ code_py_starcoder | 32.457% | 6.49B | 8.85B | 0.73 | 按供给比例分，两边同轮数 |
| └ code_py_rp1t | 1.543% | 0.31B | 0.42B | 0.73 | 已过 ast.parse 的那 209,668 行 |
| math_owm_stage2 | 26% | 5.20B | 6.51B | 0.80 | 16B 读数里数学/推理仍在陡处；与 code 共享符号结构迁移 |
| en_c4_stage2 | 16% | 3.20B | 2.40B | 1.33 | docstring 和题面是英文；低于 ~15% 散文侧先于代码侧退化 |
| textbook_30b | **10%** | 2.00B | 1.61B | 1.24 | Phi-1 的"教科书质量"那一根；拿到 cot 让出的一点 |
| cot | **8%** | 1.60B | 0.42B | 3.77 | 供给最小，8% 是**上限**不是目标——见 2.1 |
| chatml | 3% | 0.60B | 0.28B | 2.11 | 语料里几乎没有；SFT 只装被喂的范式 |
| zh_web | **3%** | 0.60B | 21.29B | 0.03 | 目标是英文代码模型 |

**code 是一个目标，摊在两份语料上。** 目标说的是"34% Python"，不是"34%
starcoder"；两份之间怎么分是一个供给事实，所以它在拆分函数里，不在目标表里。
`code_rp1t` 里过了 `ast.parse` 的 209,668 行（420,646,182 token）是我们已经
付过一遍全量扫描才确认的，和 starcoder 是同一种数据——丢掉它等于白扔 code
域 10% 的一轮供给（fb 指出）。

**按供给比例分，是唯一让两边轮数相等的分法**（都是 1.61）。没有证据说哪一份
per-token 更好，所以没有理由多读其中一份；任何别的比例都是一个没测过的质量
断言。**保持两个域而不合成一个**，因为来源和过滤都不同（starcoder 已去重且
质量过滤，rp1t_python 是我们自己的 ast.parse 一遍），合并会把两个指纹并成
一个，之后 per-role 读数就归因不到任何一边。

**zh_web 从 10.955% 降到 3% 是这次转向最干净的一个例子**：21.3B 的供给一夜
之间变得无关紧要，因为目标不再需要它。上一版里它拿 10.955% 的唯一理由就是
它多。

## 2. 两个我做了决定而不是继承的数

fb 点名要这两个由我决定。

### 2.1 每域轮数上限：cot 的 8% 是上限，不是目标

轮数上限是算出来的，不是敲进去的：`cap = ceil((used + want) / pool)`，
由脚本生成，永不手编。

**真正的决定发生在 cot 上。** 它的供给只有 0.424B：

| cot 权重 | 轮数 |
|---|---|
| 9% | **4.24**（越线） |
| 8% | 3.77 |

Muennighoff 的结果是 **≤4 轮几乎不要钱**（8.7B 模型 4 轮对单轮，最终验证
损失差 +0.5%，`ds.muennighoff_four_epoch`），过了 4 轮重复 token 开始不付账。

所以 9% 会让 cot **花钱买重读**——这是保留在 8% 的全部理由，**它是一个
供给论证，不是一个价值论证。**

**这里要撤回一句话，并且它是我自己写的规则的反例。** 初稿的理由是"cot 在
16B 读数里 0.1180 nat/B，textbook 0.5024，同样的成本 4.3 倍的实测速率"。
**`docs/standards/training_loop.md` §6 明确禁止用 nat/B 做跨角色的资源分配**
——迁移会把每个角色的 nat/B 按一个未测且逐角色不同的幅度抬高，所以跨角色的
排序不能假定成立。**那一节是我写的，然后我在下一份文档里违反了它。**

§6 里已经记着同一句话："写下限制不等于遵守它"，起因是我在给出禁令的同一份
文档里走私了一次跨角色读法，由 44 审出。**今天这是第二次，同一条规则。**
一条规则被同一个人在两天内违反两次，说明它作为原则不起作用——§6 结尾要求把
限制落成"可对着具体数字检查的测试"，而那件事还没做。

**8% 和 10% 都保留，但理由重写为：** cot 的 8% 是 4 轮线定出的**上限**；
让出的那一点给 textbook，因为**目标**把它排在下一位（Phi-1 点名"教科书
质量"这一类数据），不是因为它的 nat/B 更高。

生成器的自检对这条断言了两个方向：shipped 配置下没有任何域越线，**并且**
把 cot 调回 9% 时警告仍会响。**一个从未响过的上限，和一个响不了的上限，
分辨不出来。**

### 2.2 总预算：20B，不是继承的 30B

**先说这一节被推翻过一次。** 初版的论证是"一轮供给只有 15.45B，所以 20B"。
starcoder 实测到 8.85B（3b，59 分片外推）之后，非 zh_web 的一轮供给是
**20.51B**，那个论证死了。fb 要求重推而不是改算术，这里是重推的结果。

**结论不变，理由换了，而且新理由更弱——这一点必须写明。**

#### 先排除一个循环论证

"20B 是没有任何域越 4 轮线的最大预算"——这句话在今天的数字下是**循环的**。
20B 时唯一越线的候选是 cot（3.77 轮），而 **cot 的 8% 本身就是被 4 轮线
定出来的**（见 2.1）。用一个由预算定出的权重去定预算，不是判据，是不动点。

去掉 cot 之后，20B 时最紧的是 en_c4 的 1.33 轮——**离 4 轮线很远**。所以
**4 轮线在 20B 处对任何目标定出的权重都不起约束作用。**

#### 非循环的供给界

不依赖任何预算的量：每个域在它的目标权重下，读到 1 轮时对应多大的总预算。

| 域 | 一轮供给 | 权重 | 开始重复的预算 |
|---|---|---|---|
| cot | 0.42B | 8% | **5.30B** |
| chatml | 0.28B | 3% | 9.47B |
| en_c4_stage2 | 2.40B | 16% | **15.02B** |
| textbook_30b | 1.61B | 10% | 16.10B |
| math_owm_stage2 | 6.51B | 26% | 25.05B |
| code（合计） | 9.27B | 34% | 27.26B |
| zh_web | 21.29B | 3% | 709.77B |

**允许小域按 Muennighoff 的 ≤4 轮，第一个真正吃紧的是 en_c4，在 15.0B。**
20B 时它 1.33 轮——已经在重复，但远在 4 轮线内。

#### 那么 20B 从哪来

三条，**按强度从高到低，并且第一条不再是供给**：

1. **算力：20B = 40.5 tok/param，已是 compute-optimal（9.9B）的 2.03 倍。**
   30B 是 3.04 倍，买 0.0575 nat。**在一个同时换了形状、优化器缩放规则和
   语料的 run 上，把预算推到 compute-optimal 的三倍，是在一个三处都没有
   先例的配置上下更大的注。**
2. **重复浪费 0.6%，30B 是 1.5%。** ——注意这一条**因为 code 供给变多而
   变弱了**：初版在 4.22B code 下是 0.9% 对 2.3%，现在两边都降了一半，
   30B 的重复代价已经不大。**这一条基本不再承重。**
3. **早 13 小时拿到读数**（20B ≈ 26.5h，30B ≈ 39.7h，假设 30K tok/s/GPU×7，
   tilerl 在测真值）。

**这三条都比"供给耗尽"弱，我不掩饰这一点。** 供给耗尽是一个硬约束；
"2 倍 compute-optimal 而不是 3 倍"是一个判断。**供给多出来 5B 之后，20B
从一个被逼出来的数变成了一个被选出来的数**——而 fb 的提醒正确：多出来的
token 不等于有用的 token，**不能因为拿到了更多供给就默认抬预算，那正是上一版
配比跟着库存走的那个机制。**

**20B 扛住了 9.27B code 的冲击，这比它原先成立时更有说服力**——原先它是
供给的结果，现在它是在供给不再约束时仍然被选中的那个值。

#### 什么会让它动

- **cot 或 en_c4 的供给显著增加**：15.0B 那个界上移，25B 开始可辩护。
- **tilerl 的吞吐实测远好于 30K tok/s/GPU**：第 3 条理由变弱。
- **形状/优化器的不确定性被 shakedown 消掉**：第 1 条理由变弱，因为"不在
  没有先例的配置上加注"这个论证依赖于配置确实没有先例。

## 3. code 的权重是一个函数，不是一个常数

`--code-tokens` 是生成器的参数。3b 的抓取还没落地，surviving count 未知，
所以**权重固定在 34%（那是目标），轮数随供给浮动**：

`--code-tokens` 传的是 **starcoder 的量**，rp1t 那 0.42B 由脚本自动加上：

| starcoder 落地 | code 总供给 | 轮数 | cap |
|---|---|---|---|
| 3.0B | 3.42B | 1.99 | 2 |
| 3.8B（当前假设） | 4.22B | 1.61 | 2 |
| 6.0B | 6.42B | 1.06 | 2 |

**低于 2.5B（总供给，不是 starcoder 单独）生成器直接拒绝**，并且拒绝信息里写明**降权重是错误的修法**：
一个代码优先的目标，如果只能靠把同一批代码读四遍来供养，那是另一个实验。
要么降总预算，要么提高供给，不要降那个权重——**降权重就是让组成重新跟着
供给走**。

## 4. Python only

`ast.parse` **同时是语言识别和语法过滤**——这是它比一个语言分类器好的地方：
一个不能解析的 Python 文件和一个非 Python 文件，对这个目标是同一件事。

先例是 Phi-1：**一种语言，6B 精选 Python token，1.3B 参数上 HumanEval 50.6**。
我们在 493.6M 上用 6.8B Python token，参数少 2.6 倍，token 多 13%。

样板率的测量支持同一个方向：code_rp1t **至少 7.49%** 的 token 落在跨 ≥3 篇
文档复现的文本里（en_c4 同一把尺子是 0.16%，47 倍），而且 **6.7% 的文档
超过一半是复现文本**。质量集中在少数文档，所以丢文档比做 span 级去重便宜
一个数量级。starcoder 的 Python 切片是已经过这道工序的，rp1t 不是。

## 5. ChatML 必须进预训练

语料里实际上没有 ChatML——**每个域都低于 0.075%**。

裁定是把现有的 `问：/答：` chat 域**渲染两遍，每种格式各一遍**。不加新数据，
一处 build 侧改动。

**理由不是"多样性好"，是 200M 那一轮的实测：SFT 只装被喂的范式。** 指望
SFT 教会 base 一个它从没见过的前缀，是这个项目已经输过一次的赌。

`chatml` 是一个**新目录**，不写进任何 `data/mix_scale_*.json` 命名的目录
（chat / code / en / math / textbook / web_hq / wiki）——那些目录带着 ladder
的指纹，两天前有一个 A/B 正是因为这个在启动时被正确拦下。生成器对这条有
断言。

## 6. 每一个 epochs 值都是暂定的

**这一节不能被跳过。** 这些域都还没有 token cache，所以池子是从 stamp
估出来的：`stamp_tokens // (seq+1)` 再减 `n_val`。

**stamp 给的是 token，池子是打包后的行。** 两者差多少取决于文档长度分布，
而这正是 stage-2 那一版把 math_owm 的 cap 从 2 误标成 1 的地方。

**发车前每一个 epochs 都要对着它自己的 cache 重算。** JSON 里每条都带
`epochs_pool_source: "ESTIMATED from the stamp; no token cache exists yet"`，
不是脚注，是字段——**一个读起来像实测的暂定值，是这个仓库反复找到的那个缺陷。**

## 7. 作废条件

- **starcoder 落地量已知**：重跑 `--code-tokens <实测>`，第 3 节的表定死一行。
- **任何域建了 token cache**：第 6 节对该域失效，epochs 变成实测。
- **供给结构变化**（新的高质量域，或 starcoder 远超 4B）：第 2.2 节的 20B
  重算——它是被供给夹出来的，供给一变就该动。
- **目标变化**：整份文档作废。这是它和上一版最重要的区别——上一版的权重
  在目标变化时不会失效，因为它们本来就不是从目标推出来的。
