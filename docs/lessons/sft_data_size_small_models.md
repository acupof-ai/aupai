# ≤300M 上 SFT 数据量:格式便宜、能力不便宜,而下推到这个尺寸没人测过

**一句话给 44-17 §1:装格式的量级是每个目标行为 100–1,000 条同分布样本,这个数有受控实测
支撑(2B 上的 per-API 扫描,§2.1);但把它下推到 200M 级没有任何公开测量,而本栈自己的三臂实验
说明在这个尺寸上「量」根本不是变量,来源才是(§3)。**

先纠正我自己第一版的结论。第一版写的是「公开文献里没有任何受控 ablation」——**错的**,
受控扫描存在,而且不止一条。错因可复现:我让子代理找数,拿回一批标了 ABLATION 的条目,
**却没有区分「摘要页能证实的」和「只有全文才有的」就先下了笔**。四条承重结论去 arXiv
摘要页核,全部「不支持」;换到全文 HTML,两条完整成立、第三条数字有误。**摘要页查不到
不等于论文没说**,这两句话之间差一次取回。

## 1. 标注口径

**ABLATION** = 改变了 SFT 数据量并测量效果。**NO-ABLATION** = 只披露「我们用了多少」。
一个 NO-ABLATION 数字被当阈值引用,就是把配方读成结论。

## 2. 带受控扫描的公开测量(能当依据的)

### 2.1 Octopus v2 —— 唯一一条 per-API 数据量扫描

`arXiv:2404.01744` v6 §4.3 表 1/2,**全文 HTML 已核**。基座是 **Gemma-2B**(原句:"We employ
the Google Gemma-2B model as the pretrained model in our framework"),20 个 API,全模型微调
3 epoch:

| 每 API 样本 | 函数调用准确率 |
|---|---|
| 1,000 | **99.524%** |
| 500 | **99.048%** |
| 100 | **98.095%** |

作者的建议原句:**"a dataset size ranging from 100 to 1,000 data points per API"**。
1,000 条一个 API 的生成成本 0.0224 USD。

**这是全表最有决策价值的一条**,也是唯一一条把「每个目标行为多少条」测成曲线的。**但它在
2B,不在 300M**,而且并行/嵌套调用需要 4K/API。

### 2.2 格式与能力分离,最干净的一条

`arXiv:2305.11383`(ACL 2023 Short,Kung & Peng),**全文 HTML 已核**:

- **格式正确率 27% → 97%,每个任务只用一条训练样本**;同时 exact-match 12.78% → 43%,
  而**随机猜(在正确标签空间内猜)是 42.6%** —— 也就是说 **exact-match 的提升几乎全在
  随机基线上**。
- 200 条/任务时 exact-match 才到 52%。扫描点:10/20/50/200/800 条每任务。
- 模型是 **TK-Instruct,从 T5-large-lm-adapt(770M)训起**;**756** 个训练任务 / 119 个测试任务
  (我在全文表里读到 756;二手转述里出现过 757,以全文为准)。
- 同族发现:把指令换成「去掉全部语义、只留输出空间」的简化版,或换成输入输出映射错误的
  delusive 样本,**分数几乎不掉**(T0-3B 61.93 → 60.69)。

**读法:格式在一条样本/任务就装上了,而能力还坐在随机基线上。** 这正是本栈要的那对曲线。

### 2.3 其余受控扫描(都在 ≥1.3B)

| 发现 | 规模 | 出处 |
|---|---|---|
| 格式改善「在 100 条内饱和」,而任务表现是幂律 P=a·D^(1/b),不饱和;错误与**推理**错误相关 r²=0.98/0.99,与**格式**错误 0.93/0.83 | 7B–70B | 2410.03717 |
| IT 数据量放大 **52× 和 326×**,五个指标都没有显著变化 | 1.3B(Phi-1.5)–70B | 2402.05119 |
| 纯格式指标(IFS)在 **~8,000 条**后停在 0.9–0.95,语义指标继续升;作者称之为 "disjoint format-infusion and knowledge-infusion phases" | 7B/13B | 2307.03692 |
| 通用能力「约 1k 条就出现」,之后缓慢改善 | 7B/13B/33B | 2310.05492 |
| **≤8B 时 instruction tuning 反而伤害 held-out 表现**(容量解释:约 40 个任务吃掉小模型全部容量) | **422M**/2B/8B/68B/137B | 2109.01652 §4.2 |
| 长 CoT SFT:8k 条会掉「最多 75%」原表现;「某些特别小的模型」到 220k 仍未恢复 | ≤3B | 2506.07712(摘要只给 8k/220k 两个端点,中间阶梯与逐模型阈值需全文,**未核**) |

**LIMA**(2305.11206)那条 1,000 例是 **65B**,而它自己的量级扫描在 **7B** 上做、基线是 2,000
不是 1,000,结论是「翻倍不改善」。**1,000 以下、300M 以下,两个方向都没测过。**

## 3. 工具调用格式在小尺寸(≤1B)

| 发现 | 规模 | 性质 |
|---|---|---|
| 41,104 条训练;**解析失败 80.7% → 0.76%,格式有效率「接近 100%」,而 Correct 只 0.3% → 20.3%**;工具幻觉 0.04% → **24.7%** | **270M** | NO-ABLATION(只训一次) |
| 5,000 条合成;tool-call 等价率 9.90% → 96.04% / 38.82% → 96.71% / 23.35% → 90.86%;**格式与语义未分离** | 270M | NO-ABLATION(厂商 blog) |
| APIGen 60,000 条;xLAM-1b-fc-r BFCL **78.94%** | 1.35B | NO-ABLATION |
| 5,000 训 / 2,500 测;EM_intent 65.3、EM_structure 48.8 | **350M** | NO-ABLATION |
| BFCL:Qwen3-0.6B 总分 45.76%,**multi-turn 1.38%**;TinyLlama-1.1B 19.73% 而 **AST 全类目 0.00%** | 0.6B–1.1B | NO-ABLATION |
| 多步规划比单步掉得快得多:1000 → 98.1%,500 → 92.5%,250 → 85.3%,100 → **78.1%** | 3.8B | ABLATION |

**那条 270M 的 41,104 是全表最贴我们尺寸的一条,而它的形状正是「格式装上了、能力没装上」:
格式有效率接近 100%,Correct 20.3%,工具幻觉从 0.04% 涨到 24.7%。**

### 3.1 HuggingFace 的做法本身是一个数据点

SmolLM2(`arXiv:2502.02737`)的 SmolTalk 是 **1.1M** 对,其中 APIGen-Function-Calling 87.5k。
但 **135M/360M 用的不是它,而是 `smol-smoltalk`**(HF dataset card,我自己取回核过,共
**484,570** 行 / train ~460k)。card 上的三条改动,第二条原句:

> "We include less task specific data compared to SmolTalk"(括注:**"no function calling**
> and less rewriting and summarization examples"),理由 **"these smaller models have limited
> capacity"**。

另两条:Smol-Magpie-Ultra 的对话被**缩短**,以及**不含任何 advanced math 数据集**。

**出了 ≤360M 最好的 instruct 模型的那个实验室,在这个尺寸上把工具调用数据整段删掉,理由写的是
容量。** 这是**工程判断,不是测量** —— 他们没有给出「要多少条才够」的数,他们判断这个尺寸不该给。
(card 上没有学习率;二手转述里的「LR 提到 1e-3」我没能在 card 或摘要核到,不引用。)

### 3.2 机制侧:为什么格式便宜

`arXiv:2312.01552`(URIAL):base 与 aligned 逐 token 比,**只有 7.8% 的位置换了 top-1**,
77.7% 原样、92.2% 在 base 的 top-3 内,三对模型都是 5–7%。**换掉的位置是风格 token**
("However"、"Hello"、"sorry"),而"knowledge-intensive tokens are predominantly found in
unshifted positions",且集中在**回复开头**。

同族:Hewitt 等的 "Instruction Following without Instruction Tuning" —— **三条手写规则**塞进
product-of-experts,对 instruction-tuned 模型的胜率 **24.4%**(裸 base 只 2.4%);只训单任务
也能诱发(GSM 23.7%、诗 22.9%)。**格式便宜是因为它要改的位置本来就少**,这解释了 §2 那几条
100–1,000 条的饱和点为什么彼此一致。这两条是**分析,不是数据量 ablation**,只作机制解释。

## 4. 本栈的三臂实测:同尺寸、受控、已分离

`facts/base_eval.json 的 be.sft_v3_code500 / be.sft_v4_code500 / be.sft_v5_code500`,全部 `status: measured`,v4/v5 的 0/500 用
`rescore_code.py` 独立复算过(row_agree 500/500)。**200M 级、3.24B 预训练 token,三臂 pack
规模差 0.4%,只换 fence 行的来源**——§2/§3 任何一行都没做过这个设计。(参数数:ladder 只产
attn_every 4 一种架构,该臂实测 **206M**,数出自 `facts/data_scaling.json` 的 A/B 记录,
base_eval 里没有。)

| 臂 | pack | fence 行 | 变量 | code-500 | no-fence 率 |
|---|---|---|---|---|---|
| v3 | 46,938 行 | 15,555(33.1%) | 含切分源的同模板兄弟行 | **40.0%** (200/500) | — |
| v4 | 47,078 行 | 14,021(29.8%) | 切分源整段移除,余 4 个来源 | **0.0%** | 98.8% |
| v5 | 47,144 行 | 15,555(33.0%) | v4 + 2,300 条 Evol-Instruct 英文围栏 | **0.0%** | 99.6% |
| base | 无 SFT | — | — | 0/497 | — |

判定阈值 **12.6pt**(2δ,δ=1.4/√500)。三句读法:

1. **量不是变量,来源才是。** 三臂 pack 差 0.4%、fence 占比差 3.3pt,分数 40.0 → 0.0。
2. **v3 的 40.0% 是 in-distribution template recall,不是能力。** 500 道题**没有一道**逐字出现在
   pack 里(46,938 行全量首 24 token 精确子串探针,0/500),但切分源 `synthetic/code_python_zh.jsonl`
   仍在 `prepare_sft.py` SOURCES[7],**约 2,300–2,400 条同模板兄弟行**进了 pack。
   **corr(family 训练剂量, acc) = 0.69**(29 个 family):**≥120 条**同模板行的 family 学会
   **8/10**(sum/mean 132 行→100%,even-filter 143→89%,sum/diff 120→83%,bubble-sort 139→79%),
   <120 条的约 **0/19**。**剂量必要而不充分**:vector-sum 162 行→0%,dedup 120→0%,
   count-threshold 141→3%。
3. **跨来源不迁移,且方向是双重的。** v4 的 14,021 条**其他风格**围栏行 → 0.0;v5 再加 2,300 条
   **换生成器换语言**的围栏行、fence 率拉回 v3 水平 → 仍 0.0。而 v4/v5 的 no-fence 率
   **98.8%/99.6%** 说明**连围栏格式都没稳住** —— 与 §2.2/§3 那条 270M 同形状但更差:那条格式
   有效率接近 100%,我们这里模型几乎不产出围栏。

**两个已登记的口径限制**,不能省:(a) v3 的 40.0% 与 v2 的 2.2% 之间变的是 **document mask**
不是数据量,那一对不是数据量证据;(b) v5 的 addon **同时**换了生成器和语言,所以 0.0 证的是
「跨生成器**或**跨语言不迁移」,不能拆成两条 —— 拆开需要第二个中文模板源,今天不存在。
剂量数是**源文件行数**不是 pack 行数(方向:略高估)。

## 5. 给 44-17 §1 的口径

**该问的不是「多少对装上格式」,而是「每个目标行为多少条同分布样本」。** 四条互相独立的受控
扫描收敛到同一个量级 —— 8B 上「100 条内饱和」、770M 上一条/任务(≈756 条)、3B 上 64 条/任务、
2B 上 100–1,000 条/API —— 而 §3.2 的机制解释了为什么它们能收敛:**要改的位置本来就只有 7.8%**。

两个数并列,前者外部、后者本栈:

- **外部量级(2B,受控)**:100–1,000 条 **每 API**;100 条时 98.095%,1,000 条 99.524%。
- **本栈门槛(206M,受控)**:**同模板 ≥120 行**才学得会(8/10 vs 0/19),而**换来源不迁移**。

**两个数不冲突,但也不能相加**:前者是同一个 API 的 100–1,000 条,后者是同一个模板家族的
≥120 行,量级一致。真正的风险在**下推**,而这里有两条**实测的反向证据**:2109.01652 在
422M–8B 上测到 instruction tuning **伤害** held-out 表现(容量被微调任务吃掉),2506.07712 测到
**恢复门槛随尺寸下降而上升**,Qwen2.5-0.5B 到 220k 条仍未恢复。**没有任何公开测量在 ≤300M 上把
SFT 数据量扫成曲线**,所以这两个数是量级参照,不是阈值。

**给 206M 的实际结论:数据量不是这个尺寸的主要变量。** 本栈三臂把量控住只换来源,分数
40.0 → 0.0;§2/§3 的所有格式饱和点都在 ≥770M。**在 206M 上要先问「围栏格式稳不稳」——我们的
no-fence 率 98.8%/99.6% 说它不稳——再谈多少条。**

## 6. 没找到什么(这本身是答案)

- **≤350M 上任何 SFT 数据量扫描**:没有。最低的真实扫描下限是 8,000 条(2506.07712,含
  Qwen2.5-0.5B),Octopus v2 的曲线在 2B,EvoLM 的 50K–400K 扫描在 1B。
- **LIMA 的 1,000 例结论在 ≤300M 被验证或反驳**:都没有。最近的是 Flan 的 422M,而它扫的是
  **任务数**不是样本数,且结论是 ≤8B 会**伤害**。
- **工具调用格式有效率 vs 样本数的曲线**:任何尺寸都没找到。Octopus v2(2B)变了数据量但只
  报端到端准确率,不把语法有效率单独成列;那条 270M 把解析失败与正确率分得很干净,但只训一次。
- **Qwen 按尺寸拆分的 SFT 条数**:没有(Qwen2 ">500,000"、Qwen2.5 ">1 million",明确说
  全尺寸统一;Qwen3-0.6B 一个 SFT 条数都没给);**Qwen 任何报告都没有 0.5B 的工具使用评测**,
  尽管 chat template 里就带 `<tool_call>`。
- **Gemma 3 270M**:自己的技术报告完全不含这个尺寸,只有 blog 与 cookbook(emoji 数据集
  2,529 行、教程口径 "10-20 examples")。
- **MobileLLM 的 chat SFT 条数**:论文、附录、repo 都没有;Danube3-500M-Chat 的 SFT 数据完全未披露。
