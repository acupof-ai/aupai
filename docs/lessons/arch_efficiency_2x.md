# 200M 的架构吞吐上界

**结论：在当前证据下，2× 不是一个架构能到达的目标。** 软件侧今天没有一根
已发车的杠杆：唯一既实测又在线的是 flash seam 的 3.27%，仍是 ship candidate；
在线杠杆理想化相加 4.94%。形状重排最好的一档是 1.20×，而它要求 d/L 从 85
走到 683——朝 CompleteP 实测最优的反方向走六倍。两条路各自的上界都在 1.2×
以内，且不叠加：形状重排改的正是软件杠杆要优化的那些 kernel。

**结论所依赖的唯一一个数是 2.94× 这个实测地板**，它是今天唯一没有被任何
更正推动过的数。

这是一份否定结果。下面先给上界怎么来的，再给还剩什么杠杆，最后给这件事真正
的决策点——它不在吞吐这一侧。

## 1. 时间去哪了

稳态 trace（t57，2026-09-01，profiler 窗口 step 56–76，单卡，stage-1 shape）：

| 量 | ms/step | 占 span |
|---|---|---|
| span | 1676.63 | 100% |
| busy | 1600.25 | 95.44% |
| idle | 76.38 | 4.56% |

busy 拆成三块，后面所有推导都基于这个拆分：

| 组 | ms/step | 随什么缩放 |
|---|---|---|
| fp8 GEMM | 493.1 | 参数量（MKN） |
| bf16 LM head | 190.0 | d（vocab 固定 32784） |
| 其余（fusion / KDA / elementwise / flash / FLCE） | 917.2 | L×d（每层每 token 的带宽流量） |

**fp8 GEMM 那 493.1 ms 是地板。** cuBLASLt 实测 274.5 TFLOPS，而这块卡实测的
fp8 峰值是 279.6 TFLOPS（probes/t59_fp8_peak.py@fa8cc81，8192³，30 迭代），即
98.2%。换库最多回收 8.9 ms = 0.53%（`eff.fp8_gemm_at_realizable_peak`）。

即使 head 和其余两组全部归零，上界也只有

$$\frac{1676.63}{493.1 + 76.38} = 2.94\times$$

——2× 在物理上没有被排除，但它要求非 GEMM 部分砍掉 76%。这是下面每一条为什么
都够不着的原因。

## 2. 软件杠杆

**先分开两件在口语里都叫 CUTLASS 的事，它们的判决相反：**

| | 措施 | 余量 | 判决 |
|---|---|---|---|
| GEMM 本身 | 换 GEMM 库（CUTLASS / DeepGEMM） | 0.53% | **退役**，已在实测峰值的 98.2% |
| GEMM 周围的活 | 权重字节缓存（一个 dict） | **−20.2 ms**（路径关闭；重开即此值） | **条件性且为负**，见下 |
| 同上 | EVT / epilogue 融合余下部分 | ≤1.24%（60.2 上界减 39.4） | **已驳倒**，见下 |

用户点名问过"有没有更快的 GEMM"，所以这两条不能合并成一句话。

按收益排序的完整杠杆表。两条列的规则：**"确认它的测量"是判这一根生死的那次
测量，不是复述已有数字**；**每一行标注 ms 是实测还是推算**（fb 规则）——推算
值今天有三处偏离实测到足以改变决策，最大一处低估 5.3 倍。

| 杠杆 | ms | 实测/推算 | 占 span | 达成后 tok/s | 质量代价 | 确认它的测量 | 状态 |
|---|---|---|---|---|---|---|---|
| fp8 权重字节缓存 | **−20.2** | **实测**（t60 + t58） | −1.20% | 76.1K | 需 bit-identity 校验 | 已做，但测的是 `FP8_HEAD=1` 才装的路径 | **条件性且为负** |
| flash seam（`torch._dynamo.disable`） | 54.9 | **实测**（t57 trace） | 3.27% | 79.6K | step 110 差 0.157 nat = 1.7× twin floor，未判 | 7 卡 shipment A/B，acceptance 看 gap count + seam ms，**不看 tok/s** | ship candidate |
| EVT / epilogue 余下部分 | ≤20.8 | 推算（60.2 上界减已测 39.4） | ≤1.24% | — | 未测 | 无——没有 GEMM 可挂 | **已驳倒** |
| KDA retune（`NUM_WARPS` 解 Hopper 帽） | 0–15 | 推算 | ≤0.89% | ≤77.7K | 零（不改数值） | 一次 ncu occupancy，便宜 | pending，可能为负 |
| 单根最大可优化 fusion | 13.0 | 推算（理想 2×） | 0.78% | 77.6K | 零 | top-12 里只有这一根在 38% occupancy | 边际 |
| 换 GEMM 库 | 8.9 | **实测**（t59 峰值） | 0.53% | 77.4K | 零 | 已做 | **退役** |

**epilogue 上界从 75.5 更正为 60.2 ms**（tilerl 自审，2026-09-01）：t58 的
bf16 臂跑的是 `torch.mm(...).float()`，含一次 bf16 写加一次 fp32 转换
（≈12.9 GB/step ≈ 10.4 ms），而两个 fp8 臂都传 `out_dtype=float32`，从不付
这笔。**基线被加了候选不做的活**，这是 A/B 里最老的一种错。交叉验证：trace
里的 head 是 190.0 ms，探针报 205.3，8.1% 的差正好由这个机制解释。改用
`190.0 − 129.8 = 60.2 ms = 3.59%`。39.4 ms 的字节缓存不受影响——t60 三臂只
在"何时量化权重"上不同，GEMM 完全相同，这笔多余开销在每一臂里都有，抵消掉了。

**EVT 那一半已驳倒，不是"可行性待定"。** EVT 是 **GEMM** 的 epilogue，而
承载这笔税的三个张量没有一个来自 GEMM：G 由 Liger 的 Triton CE kernel 原地
写出，A 由 RMSNorm 写出，W 由优化器每步写一次。DeepGEMM 不是退路——SM90
路径只支持 NT 且没有 epilogue API，其 1×128 分块缩放与我们已验证的 per-tensor
e4m3 是**另一套数值配方**。乐观端要改 Liger 的 Triton kernel 本体，而那个
依赖我们已经在用源码字符串重写的方式打补丁、且在版本升级时 fail closed。
**可行性是"差"，不是"未知"。**

**在线的三根全部理想化并同时命中，是 82.9 ms = 4.94%，即 1.05×**
（seam 54.9 + KDA ≤15.0 + fusion 13.0）。
**既实测、又在线、又为正的只剩 seam 一根：54.9 ms = 3.27% = 1.034×**。

两次下修都记在这里：158.4 ms / 9.45% / 1.10× 是含 EVT 的版本，EVT 驳倒后
降到 122.3 ms / 7.29% / 1.08×，字节缓存移出在线列后降到 82.9 ms / 4.94%。
**同一天之内下修两次，两次都是因为一个数被发现测的不是它声称的那件事**：
一次是基线付了候选不做的活（`.float()`），一次是被测的代码路径根本不执行
（`FP8_HEAD=1` 缺席）。趋势不是重点，机制才是。

82.9 这个和同样是**假定三根不重叠而未联测**：seam 出自 t57 trace，KDA 与
fusion 是同一份 trace 的推算，而三者都动 917.2 ms 那一组里的 kernel。机制上
看是独立的，但"看上去独立"正是今天上午产生聚合量界定错误的那种推理。
**读作：一根实测加两根推算，假定独立，未联测。**

**字节缓存所在的代码路径当前是关闭的，所以它今天省 0 ms**（tilerl 自审，
2026-09-01，b0 独立复核）。`_fp8_mm` 只存在于 `patch_liger_flce_fp8` 装的
FLCE 路径上，而那个 patch 只在 `FP8_HEAD=1` 时运行（train.py:2143）。live run
的环境里没有这个变量，日志里 fp8-head 那行出现 0 次（只在 `ab_fp8_a.log`
里有，那是 A/B 的处理臂），而 `FP8_HEAD=1` 本身是 no-ship，−3.91%
（`eff.fp8_head_ab_noship`）。`_FP8_WSCALE` 从不被填充。

**这一行的数字是 −20.2 ms，不是 0**（fb 裁定 2026-09-01）。写 0 会让读者
以为"不亏"，而完整陈述是一个条件句，两半都要说：缓存**若** fp8 head 重新
开启省 39.4 ms；而带着缓存重开 fp8 head 是 **−59.6 + 39.4 = −20.2 ms，仍然
是回归**。缓存补上了 fp8 head 三分之二的亏空，没有补平。这是唯一能让它产生
收益的配置，而那个配置是负的。

**所以软件侧当前没有一根发车的杠杆。** 唯一既在线又为正的实测杠杆是 flash
seam 的 54.9 ms = 3.27%，它是 ship candidate 而非已发车（两臂 tok/s 都是
81K，见下）。

**3% gate 的原则保留，但今天没有实例（fb 裁定 2026-09-01，随后自行作废其
实例部分）。** gate 是一道**证据成本的门槛**：它拦的是收益小于我们测量能力、
却要占用稀缺 lane 时间和 review 注意力的改动。**规则**：gate 约束需要新依赖、
kernel 改动或 lane 时间的改动；一个没有这些成本的实测改动，按**风险**判，
不按**大小**判。原先把字节缓存当作这条规则的实例，那条裁定已作废——它裁的
是一个不运行的改动。规则对表里其余每一行都仍然生效，因为它们每一根都要付
新依赖或 kernel 改动。

结论因此更稳而非更弱：**2× 的答案不再依赖任何一根杠杆**，它整个站在 2.94×
这个实测地板上。

这就是"约 +30–40% 软件天花板"这句话被下修的地方。一条一条说明为什么这个和
更早的说法不同：

- **fp8 GEMM 换库**：早先算的是 493.1 × (1 − 0.929) = 35.0 ms = 2.09%，分母
  用的是 vendor spec 296 TFLOPS。这张卡实测 279.6。对着不存在的峰值算余量，
  2.09% 收缩成 0.53%。（原文记的是 2.06%，那是对吞吐反推的 1702 ms 步长；
  本文统一用 span，故换算为 2.09%。）
- **fp8 LM head**：roofline 说 AI = 668.7 FLOP/B，远在 H20 平衡点 37 的计算侧，
  理想 2× 值 95 ms = 5.67%。**实测是 −3.91%**（73.83K 对两个 baseline twin
  76.83/76.84K，twin 间距 0.01K）。t58 说明了原因：量化税大于 fp8 GEMM 本身
  能省的部分。这一根从收益榜上删掉；接替它的 epilogue 方案随后也被驳倒，
  只有其中的权重字节缓存（39.4 ms）活下来。
- **fusion**：早先假设 517.6 ms 是一池可回收的浪费。稳态 trace 里 273 根
  distinct kernel，top-12 中六根在 75–100% occupancy，最大的一根 41.2 ms 跑
  75%、p50 1703 µs / p95 1782 µs——分布很紧，已经饱和。只有一根
  `triton_per_fused_mul_sum_0`（26.0 ms，38% occupancy）是靶子，理想 2× 值
  0.78%。
- **launch count**：用我们自己的 trace 算过，天花板 ≤1.99%，在 3% ship gate
  以下（`eff.launch_reduction_not_a_lever`）。
- **flash seam**：机制实测（recompile 70 → 0），但**两臂 tok/s 都是 81K**。
  一个恒定的税对稳态吞吐不可见，所以这一根的 3.27% 是上界不是已兑现的收益。

在线部分相加得到 4.94%（实测部分 3.27%），不是三四十个百分点。差值来自
四处：head 从 +5.67% 变成实测 −3.91%，GEMM 库从 2.06% 变成 0.53%，EVT 从
4.50% 变成 0，字节缓存从 +2.35% 变成 −1.20%（路径关闭）。

**从这里往后，软件天花板是一根待发车的 3.27% 杠杆加至多 1.67% 的推算余量；
2× 需要结构性的东西。**

## 3. 形状重排

固定 body 参数 L·d²（容差 ±6%），受 `d % 128 == 0` 约束（hd=128 是 FlashKDA
kernel 的要求，train.py `Cfg.heads`），按第 1 节的缩放律重算 busy：

| 形状 | heads | body 偏差 | L·d | GEMM | head | 其余 | busy | 相对 | d/L |
|---|---|---|---|---|---|---|---|---|---|
| 2048×3 | 16 | ±0 | 6144 | 493.1 | 380.0 | 458.6 | 1331.7 | **1.20×** | 683 |
| 1792×4 | 14 | +2.1% | 7168 | 503.4 | 332.5 | 535.0 | 1370.9 | 1.17× | 448 |
| 1152×9 | 9 | −5.1% | 10368 | 468.1 | 213.8 | 773.8 | 1455.7 | 1.10× | 128 |
| 1280×8 | 10 | +4.2% | 10240 | 513.6 | 237.5 | 764.3 | 1515.4 | 1.06× | 160 |
| **1024×12（现状）** | 8 | ±0 | 12288 | 493.1 | 190.0 | 917.2 | 1600.3 | **1.00×** | 85 |
| 896×15 | 7 | −4.3% | 13440 | 471.9 | 166.2 | 1003.1 | 1641.3 | 0.98× | 60 |
| 768×21 | 6 | −1.6% | 16128 | 485.4 | 142.5 | 1203.8 | 1831.7 | 0.87× | 37 |
| 640×31 | 5 | +0.9% | 19840 | 497.6 | 118.8 | 1480.8 | 2097.2 | 0.76× | 21 |

机制只有一条：**参数量固定时，速度由 L·d 决定，不由 L·d² 决定。** 变浅变宽
砍掉的是每层的带宽流量，代价是 head 随 d 线性长大。两者在 2048×3 附近交叉。

上表是**推算，不是实测**。它把三组时间按 L·d²、d、L·d 外推，假设分组比例在
形状变化下不变。2048×3 距离测量点很远（L 从 12 到 3），偏差最大的会是"其余"
那一组——KDA 的 chunk 结构和 fusion 的边界都随层数变。要用它做决策，先在
候选形状上跑一次 20 步 trace。

### 质量侧的证据

CompleteP（arXiv 2505.01618）在 50M 和 300M non-embedding 上实测的 compute-optimal
N:L：50M 是 32.0（N=512, L=16），300M 是 42.7（N=1024, L=24），且随规模上升。
我们 166M non-embedding 落在这两点之间，对应的最优区间是 **32–43，而我们在
85**。

**这条证据说的是：如果为质量调形状，我们应该变深，不是变浅。** 论文自己
的话是 compute-optimal N:L 在其测量范围内 "less than ≈60"。CompleteP 参数化下
N:L≈10 仍在 compute-optimal 1% 以内，1.5B 上最深那一档省 34.4% FLOP。

按 `eff.throughput_quality_exchange_rate`（0.2b–0.3b 段斜率 0.91 nat/e-fold）
换算，每个形状的质量预算：

| 形状 | 吞吐 | 质量预算 |
|---|---|---|
| 2048×3 | 1.20× | **+0.167 nat**（可以花的） |
| 896×15 | 0.98× | −0.023 nat（要赚回来的） |
| 768×21 | 0.87× | **−0.123 nat**（要赚回来的） |

往 CompleteP 的方向走（768×21，d/L 37）要牺牲 13% 吞吐，需要质量上赚回
0.123 nat 才打平。**这是一个用户的决策，不是一个默认值**：如果目标是质量，
我们应该变深并付出速度；如果目标是速度，1.20× 是上限，且它把形状推到质量
证据的反方向六倍远。

两个必须写明的限定。第一，CompleteP 的测量在 dense softmax transformer 上，
我们是 KDA + gated MLA 混合，"其余"那一组的缩放律在他们的模型里不存在。
第二，斜率 0.91 是 0.2b–0.3b 段的割线，下一个预算点已经掉到 0.567——**这个
兑换率一个预算点内就会过期，用的时候按当时的预算点重算**。

## 4. 两条路的相互作用

**两条路是替代关系，不是互补关系。** 形状重排改的是"其余"那 917.2 ms 里的
kernel——正是 KDA retune 和 fusion 优化要动的那些。2048×3 把这一组降到
458.6 ms，KDA 的绝对余量随之减半。

反过来也一样：软件杠杆兑现之后，形状表要按新的分组时间重算，不能沿用本文
的表。**取两条路收益之和是错的**，而两份并列的杠杆清单恰好会让读者去加它。

## 5. 2× 的前提

不是这份文档能回答的，但可以说清楚它必须绕开什么：

- **fp8 GEMM 的 493.1 ms 不能靠软件动。** 要动它只能减少 FLOP——稀疏、MoE、
  更低精度，都是架构改动而非优化。
- **要 2×，非 GEMM 部分要从 1107 ms 砍到 269 ms。** 现有全部杠杆理想化相加是
  122 ms，其中实测的只有 94 ms。差一个数量级。
- **形状重排最多 1.20×，且与质量证据反向。**

所以 2× 这个目标本身需要重新提。它当前隐含"在同一个架构上"，而在这个架构上
它不可达。可达的问法是：换什么架构、花多少质量，换 2×。

## 6. 方法说明

三条影响怎么读上面数字的记录。

**测量口径。** 稳态 trace 是单卡、profiler 窗口 step 56–76。7 卡真跑的
tok/s 是 77K/GPU。本文所有百分比对的是 t57 自己的 span 1676.63 ms，不是
吞吐反推的 1702 ms——混用两个时基是已经犯过的错。

**t58 的 60.2 ms 和 ddp trace 的量化归因不能相加**，而后者的范围随后也被
推翻。前者是单卡单仪器实测上界，后者是 7 卡不同 shape 的另一次运行。我原先
写"同样的活在生产规模上同时存在于 head 和 body"——**这句是错的：那份 trace
本身是带 `FP8_HEAD=1` 抓的**（tilerl t61，`eff.fusion_and_elementwise_are_disjoint_but_the_trace_is_off_config`）。
按 Liger region 包含关系拆分，elementwise 组 250.6 ms 里有 156.9 ms 是 head
的活，四个量化算子 **92.5% 属于 head**（153.24 / 165.68 ms）。**live 侧的
量化税是 12.4 ms，不是 165.7 ms。** 机制保留，范围推翻。

**先问这段代码在 live 配置里跑不跑。** 字节缓存测得干净——预先声明、交错、
自身 spread 的 350 倍、两臂只差被测项、带 parity gate——**每一项质量检查都
通过了，而没有一项在问被测的代码是否运行**。它不运行：`FP8_HEAD=1` 缺席，
所以那条 FLCE 路径没装上。这一检查一行就够，且应当排在其余全部检查之前。

正确性与相关性是两件独立会失效的事，**查正确性的那套检查发现不了相关性
失效**（tilerl 归纳）。所以 A/B 的判据是两句：两臂只在被测的那件事上不同，
**且被测的那件事在跑**。

**找第三个数。** 今天四处自查出的错里有三处是靠一个当初没想到去查的数发现
的——trace 里的 190.0、block 分布、launch 环境。可复用的动作不是"小心"，
是**去找那个第三个数**。

**基线不能被加上候选不做的活。** 上界从 75.5 降到 60.2 就是这一条：t58 的
bf16 臂多做了一次 `.float()`，两个 fp8 臂没有。这类错误在数字上不显眼——
两臂都"跑了同一个 shape"，差的是一个 dtype 参数——但它直接决定了一根杠杆
看起来有多大。**A/B 的正确性条件是两臂只在被测的那件事上不同，而不是两臂
都跑了正确的代码。**

抓到它的动作可复用：**微基准与 trace 对不上就去追那个差**。探针报 205.3、
trace 报 190.0，8.1% 的差不是噪声，是探针在测 trace 没测的东西。

**这个问题要在两个地方问，不是一个。** 上面那条问的是"claim 依赖的路径跑不
跑"；t61 是它下一层：**claim 里根本没提 flag，是 evidence 提了**。
`FP8_HEAD` 不在那条 fact 的正文里任何位置，它在一个 415 MB trace 文件的抓取
条件里。一个从 fact 正文里读 flag 的检查会让它干净通过。

一般形式：**测量的来源是测量的一部分**。一条 fact 要记它的证据是在什么配置下
抓的，不只记它的 claim 断言什么配置。两种失效是同一个问题——这是不是 live
配置——问在两个不同的位置（tilerl 归纳）。

**不随输入移动的结论句是装饰。** 本文原先的开头写"软件侧全部余量加起来是
个位数百分比"——36 ms 的更正落下来之后它依然成立，所以它从来没有承载那个
数。已换成具体数字。一句在输入变化后纹丝不动的总结，说明它没有连着输入。

**断裂的 join 与真阴性长得一样。** tilerl 的 elementwise 归因先报"100% 不可
归因"，原因是 probe 自己的 join 断了（kernel 用 `args.correlation`，cpu_op 用
`args["External id"]`，中间必须经 `cuda_runtime` 一跳）。修好后 99.98% 可归因。
一个空结果在发表前必须先证明工具会响——这与守卫的交付标准是同一条。

同类的三处更正，都发生在本文引用的数字上：LM head 从 224.0 更正到 190.0
（224 是整个 `nvjet_tst` kernel 名族，含 attention 的 bmm）；量化税从 66 ms
到 34 ms 到实测 135.1 ms；idle 从 186.6 ms（warmup 窗口）更正到 76.38 ms
（稳态）。**kernel 名的前缀不是语义分组**，这三处里有两处是同一个错误。

量化税那一处是另一类，值得单独记：34 ms 那一版是**用一个已记录的聚合量去
界定一个未测的分量**（body 的 60.93 ms quantize 行），而分量实测 135.1 ms，
比用来界定它的聚合量还大 2.2 倍。**聚合量不构成其分量的上界，除非已知分量
确实在它里面**（tilerl 归纳）。
