# 对照实验：同一份 SFT 数据，我们的 206M vs Pythia-160M

## 1. 表头（结论之前必须先读的口径）

| | 我们臂 | 对照臂 |
|---|---|---|
| 模型 | `ckpt_p200m_4b_0902.pt` | `EleutherAI/pythia-160m` revision **step2000** |
| 参数（总） | **206,128,200** | **162,322,944** |
| 参数（非 embedding） | **172,508,232** | **85,056,000** |
| LM head | **tied**（与 `tok.weight` 共享，`train.py:472`） | **untied**（`embed_out` 是独立的 38,633,472） |
| 预训练 token | **3,999,997,952** | **4,194,304,000**（2000 步 × 1024 × 2048） |
| SFT pack（文本） | `control_sft_text_train.jsonl`，sha256 `3b443c60…` | 同一份，同一个 sha256 |
| 留出集（文本） | `control_sft_text_heldout.jsonl`，sha256 `85bd9016…` | 同一份 |
| 留出题数（文本文件） | 10,641 | 10,641（同一份） |
| **实评题数**（各按自己 seq） | **10,613**（丢 28） | **10,421**（丢 220） |
| **跨臂数所用 population** | **交集 10,421，`cae4daf7ad59388c`** | **同一个 sha256，否则不出数** |
| SFT token | **201,396,229**（49,157 行 × 4097） | **291,531,720**（142,280 行 × 2049） |
| **实训题数** | **520,274 / 521,386（99.79%）** | **510,042 / 521,386（97.82%）** |
| **实训 supervised 字节** | **588,165,773（97.37%）** | **515,476,100（85.33%）** —— 我们臂多 **14.10%** |
| SFT epoch | **1** | **1** |
| seq | **4096** | **2048**（= Pythia `max_position_embeddings`，非外推） |
| 超长丢弃 | **1,113 / 521,386 = 0.21%** | **11,344 / 521,386 = 2.18%** |
| 优化器 | Muon（2D 矩阵）+ AdamW（embedding/scalar） | AdamW（全参数） |
| lr | 既有配方 `--lr_scale` 默认 | **三点扫描 {3e-5, 1e-4, 3e-4}，取留出 loss 最低** |
| 词表 | 32,773（`vocab_id 0bce3584bc24f255`） | 50,304（tokenizer 50,277 + 2 个 ChatML special） |

**参数口径两列都报，不许只放一个。** 拿 206.1M 对 162M 是一回事，对 85M 是另一回事。
**方向对我们不利也照写**：对照模型比我们**小**，不是大。

**而且两侧的"非 embedding"不是同一个量，因为 head 一边 tied 一边没有。** 我们 206,128,200 里
embedding 只算一份 33,619,968（head 与 tok 共享权重；checkpoint 存了两份张量，state_dict 求和
得 239,748,168，减去重复的 head 才是 206,128,200 —— 这个差正好是一个 embedding 矩阵）。Pythia
的 `embed_in` 与 `embed_out` 是**两份独立权重**，各 38,633,472。所以：

- **总参数**：206,128,200 vs 162,322,944 —— 可比，我们大 27%
- **非 embedding**：172,508,232 vs 85,056,000 —— 可比，我们大 103%
- **"embedding 占比"**：我们 16%，Pythia 48% —— **不可直接对比**，因为 Pythia 把 head 又算了一遍

报表里两行都给，并把 tied/untied 标出来；只报"非 embedding"会让我们看起来大一倍而不解释为什么。

**token 量相近但不对齐**：Pythia 多 **4.9%**。写"相近（+4.9% pythia）"，不写"对齐"。

**revision 边界**：step2000 由下载 URL 路径推断，**config.json 里没有 step 字段**，文件内容无法自证是哪一步。

## 2. 这个对照能支持什么结论，不能支持什么

**能**：在同一份数据、同一 epoch 下，"我们的**数据+架构+配方合起来**"与一个同期公开基线的差距。

**不能**：把差距归因到架构、数据、配方中的**任何单独一项**。四处必然不同，每一处都是一个混杂：

1. **优化器不同**。我们用 Muon 带 2D 矩阵；在外来模型上套 Muon 是在数据之外加第二个干预。
2. **lr 不同，且不可换算**。Muon 的更新是正交化过的，它的 lr 与 AdamW 的 lr 不在同一标尺。（我第一版把 `Cfg.embed_lr × lr_scale = 1e-2` 当成"同量级"给了对照臂，**实测发散**：4 步 loss 11.52 → 13.27。1e-4 才下降到 2.49。）

   **不可换算的具体形式：我们臂根本没有"一个 lr"。** e1-27 的 40 步复现让每组的实际 lr
   第一次进了日志（`lr_scale 0.1`，step 0，warmup 1/300）：

   ```
   Muon:0    (2D 矩阵)   initial 0.01  -> 3.33e-06
   AdamW:0   (embedding) initial 0.1   -> 3.33e-05
   AdamW:0   (scalar)    initial 0.15  -> 5e-05
   AdamW:0   (attn_res)  initial 0.01  -> 3.33e-06
   ```

   **四组跨 15×（0.01…0.15），由同一个 `lr_scale` 统一缩放；对照臂是单一个 AdamW lr。**
   所以"给两臂同一个 lr"这句话**没有指称对象** —— 换算前必须先决定拿我们哪一组去对，而那个
   选择本身没有依据。这不是"标尺不同"的修辞，是**一侧是四维一侧是一维**。

   **而 `ckpt_control_ours.pt` 训练时的 `lr_scale` 原本没有任何留存记录**：`train.py:848`
   把 scale 用在 `set_schedule` 里（`initial_lr * lr_scale * m`），它既不进 `Cfg` 也不进
   checkpoint，`runs/control_ours.log` 只有 step/loss 行。§5.1 的 0.293989 是每个 lead 数的
   分母，而唯一"证据"是 `sft_math.py:53` 的默认值 0.1 —— **默认值不是记录**。已实测确认：
   `lr_scale 0.1` 重跑前 40 步与该 log **逐位相同**（1.606 / 1.629 / 1.606 / 1.663，四个
   delta 全为 0.000），而阴性对照 `lr_scale 1.0` 单调偏离到 −0.224（11 倍容差）。
   `runs/e1_27_step0/`。修在 `sft_math.py`：argv、`lr_scale`、每组 step 0 的实际 lr 进日志，
   `lr_scale` 进 checkpoint cfg。

3. **seq 不同**（4096 vs 2048，Pythia 的位置上限就是 2048）。两侧的超长丢弃数都报：0.21% vs 2.18%。

### 2.1 对照臂最初跑在 seq 1024，那个数不能用

第一版把对照臂设在 seq 1024，理由写的是"减半步耗、且绝大多数样本仍能整条放下"。**后半句是错的，而且错在量错了。**

```
control tokenizer 实测（2026-09-03，用 loader.format_example 的真模板重算）：
  seq 1024 -> held-out 丢 1,267/10,641 = 11.91% 的题，占 50.41% 的 supervised 字节
  seq 2048 -> held-out 丢   220/10,641 =  2.07% 的题，占 13.96% 的字节
  seq 4096 -> held-out 丢    26/10,641 =  0.24% 的题，占  2.83% 的字节
train 侧：seq 1024 丢 62,554/521,386 = 12.00%；seq 2048 丢 11,344 = 2.18%
我们臂 seq 4096 -> 28/10,641 = 0.26% 的题
```

**11.91% 的题承载 50.41% 的 supervised 字节**（6,183,578 of 12,266,806）—— 被丢的全是长题。"绝大多数**样本**完整"成立的同时，"绝大多数**受监督文本**完整"不成立，而 loss 是对文本算的。**报出丢弃数不等于校对过它** —— 我把这个数印在日志里印了一整轮，直到拿它和另一臂的 0.26% 并排放才看出问题。

**这一列每一行都值得看，因为它说明换到 2048 并没有让分母问题消失**：全文件分母在 1024 下虚大 2.0165×，在 2048 下仍虚大 **1.1623×**。换 seq 缩小了缺陷，没有修掉它 —— 修掉它的是"分母由实评集导出"。

那个 1024 的点位跑到 57%（step 2580/4393）被手动停掉，无 meta.json、无 checkpoint：
`runs/control_lr_scan/ABANDONED_seq1024_lr3e-5_stopped_at_57pct.log`，旁边有 README 写明**它不是观测**。它末端 lr 已衰到 2.30e-05 而 loss 还在动，把它的 2.2848 当"1024 的结果"引会是双重错误。

**这些字节数是第二版。** 第一版（12,277,447 / 6,199,868 / 50.50% / 2.02×）是用我起草 `eval_heldout.py` 时那份带尾部换行的本地模板算的，每题多 1 字节、共多 10,641 字节。差值虽小，但**它证明那份重复模板确实进过一次结论**，所以这里记下两版而不是悄悄替换。真模板是 `loader.format_example`，两个 trainer 都调它。

**对照臂做三点 lr 扫描，就是为了堵住"对照没调好"这一条**。选择依据是**留出 loss**，不是训练 loss —— 用训练 loss 选会挑出记得最狠的那个 lr，那样反驳只是从"没调好"变成"挑着过拟合选的"。

### 2.2 第四个混杂：两臂训到的文本量不同，且差额偏向我们

评测侧的三个缺陷都修掉了（同一批题、同一分母、同一统计量）。**训练侧修不掉** —— 每臂只能训自己 seq 装得下的题，所以两臂训的数据量本身就不同：

| | 训到的题 | 训到的 supervised 字节 |
|---|---|---|
| 我们臂 seq 4096 | 520,274（99.79%） | **588,165,773（97.37%）** |
| 对照臂 seq 2048 | 510,042（97.82%） | **515,476,100（85.33%）** |

**我们臂多训 2.01% 的题，却多训 14.10% 的受监督文本 —— 字节口径的不对称是题目口径的 4.4 倍。** 原因和别处一样：被丢的是长题。

**方向对我们有利，所以必须显式写出来。** 如果我们臂赢，"你们多喂了 14% 的文本"是一条真实的反驳，比 lr 和 seq 那两条更硬。判读规则因此定死：

- 我们臂领先幅度**远大于 14%** → 结论仍成立，但报告里同时给出这个让分
- 领先幅度**在 14% 量级以内** → 写"不可区分"，不写"我们赢"

这条没有靠重跑消除，是选择披露：消除它要把对照臂装不下的题从两臂都删掉，代价是重跑两臂 4 小时，且为对齐而故意削弱我方本身也需要解释。这个对照本来就只支持"数据+架构+配方合起来"，已背着优化器与 seq 两个混杂 —— 第三条量化后不改变它能回答什么。

## 3. 单位：每 supervised byte，在两臂**共同评到**的题上

两侧 tokenizer 不同，**同一份留出文本在两侧是不同的 token 数**。各自除以自己的 token 数，比的是两个不同的量。字节是两侧唯一共享的分母，而**只有 completion 参与 loss**（prompt 全 mask），所以分母是 **supervised bytes**。

**但共享分母还不够，分子和分母必须落在同一批题上。** 这里出过两个缺陷，都在出数之前修掉：

**缺陷 A：两臂评的不是同一批题。** 每臂各自丢掉自己 seq 装不下的题，于是"留出集"在两臂是两个不同的题集。修法不是"少丢"，是**在交集上评两臂** —— 题 id 取交，两臂都必须报出同一个 `evaluated_ids_sha256`，不等就不许出跨臂数。

**缺陷 B：分母覆盖全体，分子只覆盖一半。** 两臂都拿全部 10,641 题的 supervised 字节做分母，而实际只前向了其中一部分。**且这个子集不成比例** —— 被丢的是长题，seq 1024 下丢 11.91% 的题等于丢 50.41% 的字节。对照臂的 per-byte loss 因此小了 **2.0165×**，**方向是抬对照臂**（分母虚大 → loss 虚小）。分母必须由实评集导出，不能由文件长度导出。

**换到 seq 2048 并没有修掉 B。** 2048 下全文件分母仍虚大 **1.1623×**（丢 2.07% 的题 = 13.96% 的字节）。缩小缺陷和修掉缺陷是两件事。

**缺陷 C：两臂的 loss 不是同一个统计量。** 原对照臂 `eval_loss` 把 HF 的每 batch 均值按**行数**加权，即"每行均值的行平均"；我们臂 `reduction="sum"` 除以总 supervised token，是 token 加权。**8 个监督 token 的行和 900 个的行等权**，同一个名字下两个统计量。

三条同源：**一个数有两份实现。** 所以修法不是各改一处，而是合成一份 `scripts/eval_heldout.py`，两臂都走它 —— 模板、丢弃规则、分母、求和方式各只有一处定义。它的自检做过变异验证：五个缺陷各注回去一次确认变红。

**已实测的共同 population（pod，2026-09-03，两臂各按训练时的 seq 出 keep-set）：**

| | keep-set | 丢 | ids sha256 |
|---|---|---|---|
| 我们臂 seq 4096 | 10,613 | 28（0.26%） | `433e835a7859c63e` |
| 对照臂 seq 2048 | 10,421 | 220（2.07%） | `cae4daf7ad59388c` |
| **交集** | **10,421** | — | **`cae4daf7ad59388c`** |

**对照臂的 keep-set 是我们臂的真子集**（我们臂多 192 题，对照臂多 0 题），所以交集恰等于对照臂的集合、sha256 相同。这不是巧合也不是设计保证 —— 是这两个 seq 与这份数据碰出来的，换 seq 或换数据就未必。**所以判据是"两臂报出的 evaluated_ids_sha256 相等"，不是"对照臂的集合更小"。**

**交集上的分母：10,554,038 supervised bytes**（占全文件 12,266,806 的 86.04%）。跨臂数只除这个。

## 4. 数据构成（从文本实测，不要读 `src` 字段）

```
源 856,153 行 → 去重 532,027（去掉 324,126 重复）
  train    521,386 行  799,098,158 B
  heldout   10,641 行   16,190,349 B（严格每 50 条，与 train 重叠 0）
leak check: humaneval 0/164 命中、code_holdout 0/156 命中
```

**这个 leak check 覆盖的是 train↔heldout 与两个 benchmark，不覆盖任何一侧的预训练语料。**
这一点对 §5.0 的两条地板尤其重要：地板比的是两个**未 SFT** 模型在这份留出文本上的 loss，
而"这份文本有没有出现在各自的预训练语料里"没有被检查过 —— 我们的模型训在我们自己的语料上，
Pythia 训在 the Pile 上。**任一侧有重叠，那一侧的地板就偏乐观**，而地板差 2.00× 是 §5.0
"差距主体在预训练阶段"这个判断的全部依据。

**方向未知，所以不能当成有利或不利。** 要排除它得对两侧预训练语料各做一次 n-gram 命中扫描；
我们这侧可做（语料在手），**Pythia 那侧做不了**（4.19B token 的 Pile 子集不在本地，且
revision 边界本身就只能由下载路径推断，见 §1）。**所以这是一个已知而未量化的混杂，登记在此，
不由本实验解决。**

**内容构成（6,000 行全文件抽样）：36.5% 数学应用题、8.1% 带代码围栏。**

**`src` 字段会误导，不作构成依据。** 它记的是"哪个列表先产出这一行"。两个源列表的重叠比明面上多——`prepare_sft.SOURCES` 里已含 `school_math_r1_zh.jsonl`，其内容与 `prepare_sft_math` 的 `school_math_train.jsonl` 相同——所以去重保留前者，tag 读出 99.8% code_general / 0.2% math_cot，与实际内容矛盾。

## 5. 结果

**判读规则在看到数字之前写死**（fb 裁决 2026-09-03，选项 3：不重跑，改口径 + 显式披露）：

| 我们臂领先幅度（每 supervised 字节的 loss） | 结论怎么写 |
|---|---|
| **> 14.1%** | "我们的数据+架构+配方合起来更好"，同时列出 14.1% 的训练文本让分 |
| **≤ 14.1%** | **"不可区分（在训练文本不对称的量级内）"** —— 不写"我们赢" |

14.1% 是对照臂少训的受监督字节比例（§2.2）。**这条规则先定后看数，是为了让"阈值"不能事后挑。**

**"领先幅度"的分母也必须先定，否则阈值仍可事后挑。** 定为
**`lead = (ctrl_loss - ours_loss) / ctrl_loss`**，即以**对照臂**为分母 —— 这与 §2.2 的
14.10% 同口径（`(588,165,773 − 515,476,100) / 515,476,100`，分母是少训的那一臂）。判据落在
`ctrl_loss` 上就是：

```
以 §5.1 的 ours = 0.293989 计
  ctrl > 0.342246  -> 领先 > 14.1%  -> 写"更好"
  ctrl ≤ 0.342246  -> 写"不可区分"
```

**这不是形式主义**：同一个不对称换分母是 14.10% 还是 12.36%（`/ours`），阈值差 0.006805 的
loss —— 一个真实结果完全可能落在这条缝里，而**看到数字之后再选分母就是在挑阈值**。所以两个
数在这里都写出来，选中的是 `/ctrl`。

### 5.0 两条地板改变了这个结论的含义（2026-09-03Z 实测）

**两条未 SFT 地板（同一交集、同一分母）出来之后，"差距在哪个阶段产生"才可回答。**

| | 地板（SFT 前） | SFT 后 | 相对自己地板的降幅 |
|---|---|---|---|
| 我们臂 | **0.450964** | **0.293989** | 34.8% |
| 对照臂 | **0.903758** | **0.352644**（lr 1e-3，五点最优） | 61.0% |

```
SFT 前  我们领先 50.10%   （地板相差 2.00×）
SFT 后  我们领先 16.63%
```

**差距的主体在预训练阶段产生（起点 2.00×）；SFT 阶段对照追回了大部分，其中多少是地板效应、
多少是配方差异，这个实验不能分开。**

> **2026-09-03Z 修正（§5.3c）：这个 2.00× 不能整体归给架构。** 按语言拆开，对照**被训练过**的
> 英文上是 **1.5100×**（52.1% 字节），它**没训练过**的中文上是 **2.5034×**，全体加权才是 2.0041×。
> 四类 gap 分成 en-\*(1.46–1.58) 与 zh-\*(2.47–2.50) 两族，族内差 0.13/0.03、族间差 0.92 ——
> **切口落在语言上，不在内容难度上。** 所以本句"差距主体在预训练阶段产生"**按 1.5100× 成立**；
> 多出来的部分是中文暴露差，它是我们预训练的真实产物，**但不能算作架构或数据质量的证据**。

**为什么不能把 61.0% 对 34.8% 读成"对照的 SFT 配方更好"** —— 三条，每条都足以单独解释它：

1. **相对降幅不能跨起点比。** 从一个差 2 倍的地板出发，同一份数据能拉近的余量本来就大：
   离数据分布越远，第一个 epoch 拉得越多。**61.0% vs 34.8% 首先是地板效应。**
2. **两臂的 SFT 条件不对称，且方向对对照有利。** 对照扫了 5 个 lr 取最优；我们臂用既有
   固定配方，**一次没扫**。

   **这一条已经做了，而结果只解释了差距的一部分**（e1-27，2026-09-03Z，§5.3）。我们臂扫了
   `{0.01, 0.03, 0.1, 0.3, 1.0}`，最优是 **lr_scale 0.3 → 0.257765**，内点有界（1.0 回升到
   0.262356），固定配方 0.1 离最优 **+12.32%**。于是降幅从 34.8% 升到 **42.8%** ——
   **仍低于对照的 61.0%。**

   所以"我们没扫"解释了 34.8→42.8 这 8 个点，**剩下的 42.8 vs 61.0 现在是未解释的**。
   这个差额此前可以挂在"缺一次扫描"上，现在不能了，**也不能挂到任何别的没测过的东西上** ——
   第 1 条（地板效应）和第 3 条（优化器/seq）都还在，但没有一条被测量过能承担这个余量。
3. **优化器与 seq 不同**（Muon+AdamW 对 AdamW；4096 对 2048），见表头。

要把地板效应与配方差异分开，得让两臂从同一条地板出发 —— **那不是 lr 扫描能安排的**：扫描回答
的是"我们的固定配方离自己的最优有多远"，不是"两臂的相对降幅现在可比了"。

**判读规则照字面执行**：终点 lead 16.63% > 14.1%，写"我们的数据+架构+配方合起来更好"。它回答
的就是"合起来"这个问题。**不能事后改判据 —— 哪怕改的方向对我们不利，改仍然是挑阈值。**
但两行地板与 "50.10% → 16.63%" 必须与结论**并排**出现，否则"合起来更好"会被读成"我们的 SFT
配方更好"，而后者这个实验并未证明。

**判决不靠选中点。** 五个 lr 里最差的 3e-5 也让我们领先 41.24%，**没有一个点落到 14.1% 以下**
（§5.3）—— 所以"对照没调好"这条反驳关闭，且结论不依赖 1e-3 与 3e-4 谁真是最优（两者只差 0.69%）。


**未训对照臂那一行同时是拒绝逻辑的阳性对照**：它从未被错训过，所以必须通过对齐检查 ——
实测 `next-token 胜 skip-one 3.88×`，通过。若它被拒，说明是检查假阳性，而不是模型坏。

### 5.2 对照臂

**第一次扫描的三个点全部作废 —— 不是数错，是模型训错。** `sft_hf_control.py:405` 把
`input_ids=x[:,:-1]` 和 `labels=y[:,1:]` 一起传给一个**内部会移位**的 transformers 模型，
于是 seq-2048 扫描的三个点都在学"从位置 t 预测 t+2"。pod 实测（v1 点位 1 的 checkpoint，
同一批 25,215 个监督留出 token）：

```
目标 1  next-token (t+1)   7.2494 nat/token   ← 我们要的
目标 2  skip-one  (t+2)    2.7663 nat/token   ← 训练循环实际要求的，好 2.6 倍
```

**它在错目标上明显更好，所以这不是"测错了一个好模型"，是模型学的是别的任务。** 三个 `.hf`
连同我从它们算出的两个跨臂数（2.547886 / 2.831093 nat/byte）一起撤 —— 那两个数是对错目标
模型的**正确**测量。修复 `fb83968`，守卫是 `sft_hf_control` 自检 case 6。

**同一批 checkpoint 上，两个对齐给出相反的排序 —— 但这不是"错数换掉了选中的点"。**
错目标下 1e-4 领先（1.9985 < 2.5594，`eval_loss` 自己也带双移位），对齐正确的 `eval_heldout`
读出 3e-5 领先（2.5479 < 2.8311）。**两个数问的是两个问题**：指标与模型同错时排的是"谁把
skip-one 学得更好"，对齐正确时排的是"谁 next-token 做得更差"。**v2 里模型与两个指标都对齐，
两个排序就一致了**（meta 与 `eval_heldout` 都是 1e-4 优于 3e-5）。

**这一段我先写错过一次**：写成"双移位换掉了被选中的点，所以用错数选点会选错 lr"。听起来
成立，但 v2 证伪了它 —— 三个排序（v1 meta、v2 meta、v2 eval）全是 1e-4 第一。**真正的现象
是：一个与模型共享同一错误的指标，量的是这个错误学得多好。** 排序差异来自**模型训错**，
不来自"读了哪个字段"。


**为什么同一个 bug 修过一次还在**：`eval_loss` 有一模一样的缺陷，`0f9d587` 修掉了 —— 一个
commit、一个调用点。当时记下的 cause 是"**评测器**双移位"，所以修到评测器就停了。真 cause 是
"**在这个文件里**，对 transformers 模型预移位就是双移位" —— 那是文件的属性，不是某个函数的。
**cause 记窄一格，同族的其余调用点全部留在原地。** 而 :405 的注释还写着 "train.py's
convention"，那句话对**我们臂**是对的（`HybridLM` 在循环里算 loss、不内部移位：`model.py:536`、
`sft_math.py:214`），抄到这里就是错的。

**我们臂不受影响，已核**：`sft_math.py:108-109` 只移一次，`HybridLM` 不内部移位。§5.1 的
0.293989 成立。

**第二次扫描（`runs/control_lr_scan_v2/`）**：三点并行在卡 0/1/2，代码 sha `e83c9e50`。
除 `--lr`/`--out` 外每一项超参与 v1 逐项相同（`ARGV_DIFF.txt` 机器核对，八项全 same）。
待回填：三点的正确留出数、选中点、跨臂数。

**选点只读 `eval_heldout.py`。** 跨臂数必须落在**交集**上、按**字节**算，而 `meta.json` 的
`held_out_loss` 是**臂内 per-token** 数（两侧 tokenizer 不同，per-token 不跨臂可比）。
选中点的 `evaluated_ids_sha256` 必须等于 `cae4daf7ad59388c`，**不等则不出跨臂数**。

**这里我说错过一次，纠正记下来。** 我曾断言（对 1e 两次、并写进本文与 v2 README）
`meta.json` 的 `held_out_loss` 用**全文件分母**、v1 的顺序翻转就是读它读出来的。**两条都错：**

- `held_out_supervised_bytes = 12,266,806` 确实是全文件，**但它是一个被记录的字段，不是
  `held_out_loss` 的除数** —— `eval_loss` 除的是监督 token 数。而 `pack_rows` 是**打包**不是
  丢弃（10,641 例 → 2,897 条密集行），所以它评的几乎是全部例子。**证据**：v2 lr 3e-5，
  meta `1.4445` vs `eval_heldout` per-token `1.4434`，差 **0.08%** —— 真是分母之差不可能这么近。
- **顺序翻转不在 meta 与 `eval_heldout` 之间。** 三个排序全是 1e-4 第一（v1 meta、v2 meta、
  v2 eval）。翻转在 **v1 内部两个数之间**：带双移位的 `eval_loss` 读 2.5594/1.9985（1e-4 先），
  对齐正确的 `eval_heldout` 读 2.5479/2.8311（3e-5 先）—— **同样三个 checkpoint，两个不同的
  问题**。前者指标与模型同错、排的是"谁把 skip-one 学得更好"；后者排的是"谁 next-token
  做得更差"。v2 里模型与两个指标都对齐，它们就一致了。

**我怎么错的**：`held_out_supervised_bytes` 紧挨 `held_out_loss`、前缀相同，我**推断**它是除数，
没去读 `eval_loss` 的返回语句。又一次"用取值的合理性推断结构"，与 §6 表里两条读错键同根。


**两条地板（未 SFT 基线）已测**：未 SFT 的 Pythia-160M step2000、未 SFT 的
`ckpt_p200m_4b_0902.pt`，都在同一交集上，读数见 §5.0。没有它们，读者分不清对照臂的数是
"SFT 没学会"还是"模型本来就这样" —— 而 v1 已经证明**确实可能是前者**。

loss 最优落在同一个 lr（1e-3），这是巧合还是有关系，本实验不答。

对比 v1 那个错目标 checkpoint：skip-one **赢** 2.35×。**方向翻转且幅度大** —— 训练目标确实修

minimum"*。而判读边界是 `ctrl > 0.342246`，当时的选中点 0.355095 **只高出 3.8%** —— 对照的最优
是不是 3e-4，直接决定"我们更好"还是"不可区分"。**方向对我们不利，所以不能省。** 只补 1e-3 不够：
若它仍在降，最优又落在端点；1e-3 与 3e-3 同时跑才可能把最优夹住（1e 裁决，并行不增加墙钟）。

**事后：这个预判对了一半。** 最优确实不是 3e-4（是 1e-3），余量确实缩小了（3.75% → 3.04%）；
但**没有预见到的是**五点会显示"任何 lr 都进不了不可区分区间"，而那才是让结论稳的那条。
**扩点是为了防守一个可能翻盘的风险，收获的是一个更强的结论** —— 两者不是同一件事。


**"训练 loss 会不会选出不同的点"—— 本配置下不会（五点实测）：**


**五点让这条比三点时强，但也更窄。** 3e-4 与 1e-3 的训练 loss 差 **0.0002**（1.1099 vs 1.1101，
**顺序与留出相反**），而留出差 0.0070 —— **训练 loss 在这两点上已经分辨不出谁更好，靠它选点会
选到 3e-4**。结论不变（两点都过边界），但"两个指标一致"在这里只在**排除 3e-3 和小 lr** 的意义上
成立，**不足以在最优附近选点**。选点依据仍然只读 `eval_heldout`。

`runs/control_ours.log`（四个差都是 0.000），而 lr_scale 1.0 发散到 −0.224。

**为什么不换成 26.91%，尽管它对我们有利 +10.27 个点**：已发布判决用的是固定配方，**看到结果之后

`scripts/e1_27_table.py` 自己把它打出来，不依赖谁记得。

**这次扫描回答的是"我们的固定配方离自己的最优有多远"（+12.32%），不是"两臂的相对降幅现在
可比了"。** 后者需要两臂从同一条地板出发，lr 扫描安排不了。**42.8% 仍低于 61.0%，那 18 个点的
余量现在是未解释的** —— 见 §5.0 第 2 条改写。


**八个测量里七个带两个对齐守卫，第八个是 `0.293989` —— 每个 lead 数的分母。** 它 18:18Z 写

检查过。它自己的**地板**过了（6.07×），但**地板过关不代表训练好的 checkpoint 对齐** ——
trained-wrong 恰好是 ln(V) sentinel 盲的那一格（写在它 docstring 的六行范围表里），能看见它的
是 skip-one。

**"我们臂用的是另一个 trainer 所以不会有这问题"不算证据。** 那正是 `0f9d587` 修掉 `eval_loss`
一个调用点之后 `:405` 还站着的同一套推理 —— cause 记窄一格，同族调用点全部留在原地。所以是
重打，不是论证。

### 5.3c 地板差按语言拆解：混杂成立，1.51× 才是架构主张能拿的数（e1-29，2026-09-03Z）

**这一节下调我们自己已经写下的主张。** §5.0 把地板差 2.00× 读成"差距主体在预训练阶段产生"，
而对照是 Pythia-160M，训在 the Pile 上——**英文语料**。所以 2.00× 里有多少是"我们更强"、
多少是"我们见过中文而它没见过"，此前从未被排除。**这个混杂对我们有利，所以它被测了。**

同一交集 10,421 题（sha `cae4daf7ad59388c`，两臂 ours-only 0 / control-only 0），
按**实测内容**分四类（不读 `src`，理由见 §4）：

| class | n | bytes | ours | ctrl | gap |
|---|---|---|---|---|---|
| en-code | 704 | 3,164,072 | 0.434174 | 0.631933 | **1.4555×** |
| en-prose | 733 | 2,332,340 | 0.436729 | 0.691585 | **1.5836×** |
| zh-code | 185 | 227,984 | 0.344330 | 0.850544 | **2.4701×** |
| zh-prose | 8,799 | 4,829,642 | 0.473872 | 1.186816 | **2.5045×** |
| **英文合计** | 1,437 | **5,496,412（52.1%）** | 0.435258 | 0.657246 | **1.5100×** |
| **中文合计** | 8,984 | 5,057,626（47.9%） | 0.468032 | 1.171657 | **2.5034×** |
| **全体** | 10,421 | 10,554,038 | 0.450964 | 0.903758 | **2.0041×** |

**判决的依据是两族分离，不是任何单个数。** 四类极差 1.049，但它们不是散开的——
**en-\* 落在 1.46–1.58，zh-\* 落在 2.47–2.50。族内差 0.13 与 0.03，族间差 0.92。**
切口落在**语言**上，不在代码/散文上。**如果切口落在代码/散文上，那才是"内容难度"解释；
落在语言上，只有语言暴露能解释。** 中文 gap / 英文 gap = 1.658。

**三个数各自管什么，不能混用：**

| 数 | 支持什么主张 |
|---|---|
| **1.5100×** | 架构 + 数据质量的下限 —— 在对照**被训练过**的语言上 |
| **2.5034×** | 语言暴露差 —— 在对照**没训练过**的语言上 |
| **2.0041×** | 全体字节加权，两者混合，**不能单独归因于任何一方** |

**中文暴露不是"不算我们的"，是"不能算架构的"。** 它是我们预训练的产物、是真实能力，
只是不能拿来支持"架构/数据质量更好"这个特定主张。**§5.0 那句"差距主体在预训练阶段产生"
按 1.5100× 成立，不按 2.0041× 成立**；差额归中文暴露。

**两臂都逐位复现了自己发表的地板**（在重算的共享总体上）：ours `4759488.226891` 对
`4759488.226890564`，control `9538300.020111` 对 `9538300.020111084`。所以对照侧现在有
**复算一致性**，而不只是**权重同一性**（其五个文件 sha256 对上 `runs/e1_control_model_fp.json`）——
**这是两个不同的主张，审计里必须分开。** §5.2 那五个对照 SFT checkpoint **都在**

确认），所以它们两者都可以补——复算一致性尚未验，但**可验**。

> **本节初稿写的是"模型已删，连字节都核不了"，那是假的。** 我用
> `find /work /tmp -maxdepth 3 -name 'pythia*'` 找过，没找到，就写了"已删"——而实际路径深度是 5，

### 5.3d 干净子集上的四点判决（e1-28，2026-09-03Z，10,105 题 / sha `7231156c5698c210`）

**去掉 e1-28 标记的 316 题之后，四个点都有了，判决不依赖用哪个总体。**

### 5.3e 生成式评测：demo 语言不是主因，而"能力"这个词一个数都撑不起来（e1-31，2026-09-03Z）

**为什么要有这一节。** §5.0–§5.3d 全部是**似然**：教师强制下的 nll/byte。用户问的是"训了之后有什么分数能看出来"，
而似然回答不了它——**留出集与 SFT 训练集同源，我们的预训练语料本来就更接近它。** 英文的 1.51× 剥掉了语言层，
没剥掉语料风格层。所以这一节换成**生成式**：模型自己写，判对错。

math-500，3-shot 续写（**不用 ChatML**：预训练语料里 `<|im_start|>` 在 168,000 行采样中出现 0 次，
零样本 ChatML 测的是模型对一个训练中不存在的前缀的反应，见 AGENTS.md），497 题（3 题作 demo 排除），
贪心，`max_new 512`。**demo 语言做成一个轴**，题目始终是中文，所以是干净单变量：

| cell | accuracy | answer-present（**臂间不可比，见下**） |
|---|---|---|
| ours + zh demos | 27/497 = **5.4%** | 37.0% |
| ours + en demos | 17/497 = **3.4%** | 30.6% |
| control + zh demos | 0/497 = **0.0%** | 0.6% |
| control + en demos | 0/497 = **0.0%** | 1.0% |

**accuracy 四格全在 2δ = 12.6% 之下，按预注册判据读作零，四个数之间不做任何比较。**
5.4% 与 3.4% 之间没有可解释的差异。

> **answer-present 的臂间比较未定，因为两臂在不同的停止规则下生成。** 我们臂跑的是**没有重复停止**的
> 解码器（缺陷见下），中位 794 字符；对照臂**有**重复停止，中位 86 字符。而我们臂的答案标记
> **出现在第 287 字符（中位）、第 442 字符（p90）**——**对照臂在到达那个位置之前就被掐掉了。**
> 84–86 个字符里塞不下一个完整解答，**所以对照臂没有产出格式的机会**，0.6% 不是"它不会"，
> 是"它没被允许写到那里"。
>
> 我先前把这一栏标成"量的是格式获得不是能力"——**那还不够，它连格式获得都不干净。**
> 我当时验的是"`model_turn` 在生成之后截断"，**没验"对照臂是否曾产出足以到达标记的文本"**（6e 指出）。
> **要救它只有一条路**：`--no_rep_stop` 两臂在同一解码器下重跑四格。**这不是补充实验，是这一栏的前提。**
> 未做，登记在此。**accuracy 不受影响**（打分在 `model_turn` 截断后的文本上，且四格全部读作零）。

**demo 语言不是主因**，这是这个轴存在的目的。**但这个结论现在只在 accuracy 上成立（四格全零，无差异），
在 answer-present 上待重跑**：原先的"36.4pt vs 29.6pt 同一量级"用的是被停止规则污染的那一栏。
demo 语言在同一臂内部仍是干净单变量（同一个解码器），所以**臂内**的 37.0→30.6 和 0.6→1.0 可读：
**我们臂动 6.4pt、对照臂动 0.4pt。**

**answer-present 即使重跑干净，量的仍是格式获得，不是能力。** "生成里有一个能抽出来的答案"和"那个答案对"
是两个不同的主张，而同一批生成的 accuracy 读作零。**我们语料里有 boxed 答案形状的中文数学解答文本，
Pile 里没有**——这是**分布事实**，方向对我们有利，是能力的**前置条件**，不是能力。


**对照那 0.6% 里有多少是停止规则的份额，目前未分离——但已知它不是零。** 量了标记出现在生成里的哪个位置：

```
cell         有标记      标记位置 中位/p90    生成长度 中位
ours-zh     267/497        287 / 442            794
ours-en     162/497        381 / 449            851
control-zh    3/497         14 /  14             86
control-en    5/497         13 /  22             84
```

**我们臂的标记中位落在第 287（zh）／第 381（en）字符，而对照臂整条生成只有 84–86 字符。**
对照臂在到达那个位置之前就被重复停止掐断了，**所以它没有产出格式的机会**——0.6% 不是"它不会写"，
是"它没被允许写到那里"。反过来，对照臂那 3–5 行有标记的，标记在**第 13–14 字符**：它们是直接抄
demo 开头的标记，不是写完解答后给出的答案。
分离需要 `--no_rep_stop` 两臂同解码器重跑四格：**长度上去且 answer-present 跟着上去 ⇒ 停止规则占了份额；
长度上去而 answer-present 不动 ⇒ 是行为差异。** 未做，登记在此。**这不是补充实验，是那一栏的前提。**

> **本节初稿的一个缺陷，以及它作废了什么。** `train.generate_batch` 用 `tokenizer is not None`
> 开关重复停止（`train.py:944`），而本文件的调用没传这个参数——**所以我们臂跑的是没有重复停止的解码器**，
> 而对照臂（我显式传了 tokenizer）有。因此 d165a905 里所有**长度**与**循环率**数字
> （ours 794–851 字符 / 98.8% 循环，control 84–86 / 77.7–86.9%）**是在两个不同解码器下测的，作废**。
>
> **我原来只作废了长度和循环，把 answer-present 留在台上，理由是"打分在 `model_turn` 截断之后"——
> 这个理由不成立（6e 指出，我复核确认）。** 我验的是"`model_turn` 在生成之后截断"，
> **没验"对照臂是否曾产出足以到达标记的文本"**：上面的位置分布说它没有。
> **`model_turn` 之后的截断不能补回停止规则之前就没生成出来的字符。**
> 故 **answer-present 一栏与长度/循环一同降级：臂间比较未定**。
> **accuracy 不受影响**（四格全部读作零，无可比较者），**demo 语言结论只在 accuracy 上仍立**。
>
> 修法：`--no_rep_stop` 通到两条解码路径、`rep_stop` 进摘要 JSON、preds 路径带 `.norepstop`——
> **解码器从"哪条分支恰好传了哪些参数"变成一个被记录的变量**（`c8acbd0f`）。
>
> **教训（与本周另两例同形）：一个作废的前提，其影响面要按"它污染了哪些字符"算，不是按
> "哪个函数在它之后运行"算。** 下游函数运行得再正确，也复原不了上游从未产出的输入。

**抄袭与循环不区分两臂**，这一点我原来的读法也是错的：两臂都在 90%+ 的生成里含有一段 12 字符的 demo 原文，
按占比算**我们抄得更多**（中位 39.7% vs 21.3%）。**一个已经饱和的比例对差异不敏感——它不是弱证据，是零证据**，
而 93.6% 这个数字很大，看起来像强证据。诊断脚本 `eval/l1_2x2_diagnose.py` 因此同时报 rate 和 share。

**产物**：`runs/l1_2x2_{ours,ctrl}_{zh,en}.json` + `.log`、`runs/l1_2x2/preds_*.jsonl`（各 497 行）、
`runs/l1_2x2_diagnose.json`。

**math-500 对我们臂是真留出，不是背题**：`data/eval/holdout_hashes.txt` 2,533 条对 math_test_500
**500/500 全命中**，而两臂训的那个 pack `data/sft/control_sft_ours.pt` 记录 `holdout_fp: 23427f4e7087a8b7`，
**与该 hash 文件逐字节一致**。核的是 fingerprint 而不是 `is_holdout()` 是否存在——
账上有过该文件为空导致 19/20 题漏进 SFT 的先例，**而空文件与正确文件在函数行为上只差一个静默的 False**。

## 6. 过程中修掉的、会污染这个结论的东西

按被发现的顺序，每条都在上卡前：

| 缺陷 | 后果（若未修） |
|---|---|
| pack 未洗牌（`prepare_sft` 洗，我这个没洗） | 两臂各按来源顺序训练，最后看到的来源主导结果；且与 `be.sft_v3/v4/v5` 不可比 |
| 留出集由每臂各自切 | 我们臂会训练在对照臂的验证集上，且多训 2% |
| `resize_token_embeddings(len(tok))` | 把 Pythia embedding 从 50,304 缩到 50,279，**丢 25 行训练过的权重** |
| 对照臂 lr 1e-2 | 发散；结论会变成"我们赢"而实际是对照炸了 |
| leak 检查在空 population 上返回 clean | 0 行 pack 被标记为"干净" |
| `check_sft_ready` 带子 `(0.5, 60.0)` | 拒绝 repo 里**每一个**真实 pack（实测都在 79.3%） |
| `run_sft.sh` 硬编码卡 0 | 两臂撞同一张卡，表现为"对照很慢" |
| `card_claim` 记 `os.getpid()` | 锁永远批准；两个 job 都拿到同一张卡 |
| `sft_math.py` vocab assert 守卫读错键 | 错词表 pack 会静默以 ~4 倍 loss 训练 |
| `run_sft.sh` 从不传 `--hypothesis` | exp 行的假设永远空白 |
| 两臂各评自己的 keep-set | 两个 loss 落在不同题集上（10,613 vs 10,421），差多少都不说明问题 |
| 分母取全文件字节、分子只覆盖 keep-set | per-byte loss 虚小：1024 下 2.0165×、2048 下仍 1.1623×，**方向抬对照臂** |
| 对照臂按行加权、我们臂按 token 加权 | 同名两个统计量；8 个监督 token 的行与 900 个的行等权 |
| 对照臂 seq 1024 | 丢 11.91% 的题 = **50.41% 的 supervised 字节**；"对照没喂饱"是条现成反驳 |
| 我起草的 `eval_heldout.py` 自带一份模板副本（带尾部换行） | 每题多 1 字节，且打的分是两个模型都没训过的串 |
| 加权自检用常数 logits 的假模型 | 行均值与 token 求和恰好重合，**这条自检分辨不出它要分辨的两件事** |
| **`sft_hf_control.py:405` 训练循环双移位** | **三个 checkpoint 训在错目标（t+2）上，整轮扫描作废** |
| 打分器的 ChatML id 无人核对 | id 撞了则停止符是模型没训过的 token，loss 只是**偏高一点** —— 又一个像合理结果的错数 |
| `eval_heldout.py --selftest` 缺 `data/tokenizer.json` 时抛异常 | 别人的 commit 在 hook 里崩，读起来像仓库坏了（实际发生，两个 session） |
