# Ranked defects — impact on "train a 200M model to do Chinese grade-school math"

## 1. Eval integrity: nothing removes the 500-problem holdout from the SFT corpus, and no script produces the split
`prepare_sft.py:33` (also `scripts/fetch_math_data.py:157`)
**Defect:** stage-1 SFT trains on the full 223,423-row `data/school_math_r1_zh.jsonl`, the same Belle-derived corpus the 500 eval problems come from, with no exclusion step anywhere.
**Failure:** `grep -rln math_test_500` returns exactly one file (`eval/math_zh.py:27`); nothing in the repo or in `git log --diff-filter=A` ever created `data/eval/math_test_500.jsonl`, `school_math_train.jsonl`, or `gsm8k_zh_train.jsonl`. `sft_math.py` resumes from the stage-1 checkpoint, so 32.2% may be partly memorization, and the split cannot be regenerated or audited. Every delta in EXPERIMENTS.md rests on it.
**Fix:** commit the 500 holdout question-hashes; filter them in `read_examples()` and in `fetch_math_data.py`. Re-score once to get a trustworthy baseline before any further tuning.

## 2. `tail_answer` writes wrong gold answers into the math corpus (three mechanisms)
`scripts/fetch_math_data.py:70-87`
**Defect:** the answer extractor prefers pattern order over position, has a character class that excludes `,` and `\frac`, and falls back to a regex that returns the textually last number.
**Failure (measured on real data, running the file's own functions):**
- `LAST_NUM` (:75) on a fraction tail returns the denominator. On 60K rows of `school_math_r1_zh.jsonl`, 1,947 kept rows (3.6%) emit the denominator: row 1 becomes `…\boxed{\dfrac{10}{3}}…\n答案是：\boxed{3}` — the appended gold contradicts the prose above it.
- Pattern order (:81): `答/答案` (index 0) beats `####` and `\boxed{}`. `"解答：\n\n1. **…"` matches `答：\n\n1.`, `num("1.")` parses, and 1,008/29,153 mxode rows (3.5%) get gold `\boxed{1.}` for a problem whose answer was 17.
- Comma (:71): `答案是：1,200` → `1`; 76/7,471 gsm8k_zh rows (1.0%) mislabeled.

`sft_v3`'s recorded symptom ("answers division with quotient-and-remainder where gold is a fraction") is this. sft_v3/sft_v4 were both trained on this fetcher's output.
**Fix:** add `\\d?frac\{([^}]+)\}\{([^}]+)\}` and `,` to `ANS_TAILS`, and select the match with the largest end offset across all patterns instead of returning on the first pattern.

## 3. SFT packing trains ~20% of loss tokens on answer prose with no question
`prepare_sft.py:99-105` (identical at `prepare_sft_math.py:93-98`)
**Defect:** over-length examples are tail-truncated (deleting the prompt) and `plen` collapses to 0; separately, examples are concatenated into 4097-token rows with no document boundary.
**Failure:** measured with the real tokenizer — s1k 865/1000 truncated, 850 lose the whole prompt; openo1 951/77,685 truncated, 805 lose the prompt → 6.78M tokens (3.9% of the 174.1M loss tokens in the shipped `data/sft/sft_all.pt`) are headless reasoning fragments at full loss weight. Packing adds more: 9.54 `<eos>`/row, `(labels[:,0] != -100).mean() == 0.811`, and 16.4% of all loss tokens are answer tails orphaned across a row boundary. There is no doc mask — `train.py:210` is `flash_attn_func(causal=True, window_size=(1023,0))` and KDA carries recurrent state across the whole row — so the model is conditioned on ~1000 tokens of an unrelated problem while answering, then at eval sees a bare `问：…\n答：` with zero context.
**Fix:** drop examples longer than `row_len` instead of tail-truncating, and greedy-pack (start a new row when the next example does not fit, pad the remainder).

## 4. The single-binary-op equation regex misparses every chained expression
`filters/clean_school_math.py:6` and the identical `eval/math_zh.py:29`
**Defect:** `EQ` matches only `a op b = c`, so on `a op b op c = d` it anchors the last two operands and computes the wrong sub-expression, then declares the line wrong instead of skipping it.
**Failure:** `"45 + 57 + 54 = 156"` → `[('57','+','54','156')]` → 111 ≠ 156. `strip()` at :10 rewrites `\frac{1}{4}` → `1/4`, so `20 × 1/4 = 5` → `[('1','/','4','5')]`. Re-running the filter over 20,000 rows: 824/14,527 (5.7%) dropped as `bad_eq`, ≥41% of them arithmetically correct — i.e. ~3.2% of rows silently deleted, biased exactly toward the 3+-operand multi-step problems the model fails on. On the eval side, `check_steps` over known-correct gold flags 397/1183 = 33.6% (math-hard) and 439/2874 = 15.3% (school-math) as wrong, so the `step-eq wrong N/M` line behind the EXPERIMENTS.md:36 conclusion "the arithmetic inside it is wrong" has a 15-34% false-positive floor.
**Fix:** reject a match whose immediate left/right context is another operator+operand (or evaluate the full chain); skip what cannot be parsed rather than scoring it wrong.

## 5. GRPO trains on forced-EOS padding and its "length normalization" is a no-op
`algorithms/rlvr_trainer.py:66-68`, `algorithms/rlvr_generate.py:30-35`
**Defect:** `generate` steps until *all* n sequences finish, forcing `eos` into finished rows, and returns a rectangular slice; `grpo_loss` masks in the whole row.
**Failure:** 7 of 8 rollouts stop at token 30, one runs to 512 → each short row is `[31 real tokens, 481 forced <eos>]`, all inside the loss mask. Those filler tokens were produced by `torch.where(finished, eos, nxt)`, not sampled from the policy, so the gradient is biased; and `<eos><eos>` never occurs in the packed SFT data, so their log-probs are large-negative and dominate `seq_lp`. With `adv>0` most of the update maximizes `P(<eos>|<eos>…)`. Since every row shares `mask.sum(1)`, line 78 divides by a group constant — the advertised length normalization never runs.
**Fix:** truncate each `g` at its first `eos` before building the mask (or return per-row lengths from `generate`).

## 6. The weight-decay ramp overwrites the embedding group's decay with 100× its configured value
`train.py:951-952`
**Defect:** the ramp loops over all three optimizers and unconditionally sets `g["weight_decay"] = Cfg.muon_wd * (1 - step/total)`, but only `initial_lr` was cached (:945 has it, weight decay has no equivalent).
**Failure:** `opt_embed` is AdamW with `weight_decay=Cfg.embed_wd=0.001` (:629). At step 0 the guard `"weight_decay" in g and g["weight_decay"] > 0` is True, so the 33.6M-param tied tok/head matrix is decayed at 0.10 with lr 0.1 for the entire run. `Cfg.embed_wd` is dead config, and the loop re-reads what it wrote, so the value is unrecoverable. `opt_scalar` escapes only because its wd is exactly 0.0. The momentum ramp one line above is correctly Muon-only, so per-optimizer gating was the intent.
**Fix:** `if opt is opt_muon:` around the weight-decay line.

## 7. `short_conv.weight` is routed to the scalar AdamW group at 15× the Muon LR
`train.py:610-619`
**Defect:** the router is `tok/head → embed; ndim == 2 → muon; else → scalar`; `nn.Conv1d` weight is `(1024, 1, 4)`, ndim 3, so all 9 KDA short convs land in the group meant for RMSNorm gains and 1-D biases at `scalar_lr = 0.15` (:117), wd 0.
**Failure:** init is `U(-0.5, 0.5)`; AdamW's normalized step is ≈lr. In `ckpt_k3-mla_2b_step2000.pt` the short-conv weights have gone from absmean ~0.25 to 1.7-2.9 with max 9-16 — a ~10× magnitude blow-up in 2000 steps, on the same module the last commit had to fix for a causal leak. The docstring at :602 states the intended split explicitly, so this is a misroute, not a choice.
**Fix:** `elif p.ndim >= 2:` → Muon (reshape `(d,1,k)` → `(d,k)`), or give conv weights their own AdamW group at ~0.01.

## 8. Logit softcap is applied at inference only, never in the training loss
`train.py:465`
**Defect:** `15*tanh(z/15)` lives inside the `targets is None` branch; the training branch returns raw hidden to Liger FLCE. Git shows the cap used to sit *before* the branch (commit 8af8ec3) and was orphaned by the FLCE refactor.
**Failure:** training never penalizes large logits, so they grow past the cap. A correct-token logit of 30 vs 20 becomes 14.46 vs 12.72 → p drops from ~0.99995 to ~0.85. `eval_ppl.py:48` and `eval/run_eval.py:203` score under a distribution the model was never fit to, so reported PPL and CEval/MMLU option scores are not comparable to the FLCE val loss; `algorithms/rlvr_trainer.py:75` takes policy log-probs through the same capped path. Greedy math decoding is unaffected (tanh is monotone).
**Fix:** one line — apply the cap before FLCE, or delete it from the inference branch.

## 9. Sharded eval reports an accuracy over a truncated row set, and `run_sft.sh` records it as the official result
`scripts/eval_math.sh:9,14-18` (identical `scripts/eval_hard.sh:9`), `scripts/run_sft.sh:34-35`
**Defect:** bare `wait` returns 0 regardless of child status, and the merge heredoc never asserts `len(rows) == 500`.
**Failure:** shard 3 OOMs after writing 40 of 84 rows; `eval/math_zh.py:90` opened the preds file with mode `"w"`, so a valid partial file remains. `wait` → 0, the grep at :10 still matches 5 shards so `set -e` never fires, and the merge prints `TOTAL math-500: 148/456 = 32.5%`. `run_sft.sh:34` keeps only `tail -1` and writes it into `runs/experiments.jsonl` and EXPERIMENTS.md. Reproduced end-to-end (simulated shard-3 failure → `TOTAL math-500: 154/460`, exit 0). Fully silent variant: a shard dying *before* :90 while stale `preds_{ckpt}.{i}.jsonl` from an earlier eval sits on disk — count still reads 500. Second bug in the same line: `RESULT=$(… | tail -1)` under `set -euo pipefail` aborts `run_sft.sh` before `exp.py done`, leaving the row `status="running"` forever (`exp.py:115` binds to the newest running row, so a re-run never closes the orphan).
**Fix:** collect PIDs and `wait $pid || exit 1` per shard; assert `len(rows) == n_expected` in the heredoc; wrap the eval call in `set +e` / `EVAL_RC` like the train call at :24-32.

## 10. The NaN-recovery guard restores nothing, may never arm, and leaves no trace in the log
`train.py:959-962`, `sft.py:157-158`, `sft_math.py:165-166` (+ `:107`, `:143`)
**Defect:** three compounding bugs in one mechanism.
**Failure:**
- `{k: (v.cpu().clone() if torch.is_tensor(v) else v) for k, v in opt.state_dict().items()}` — `state_dict()` returns exactly `{"state": dict, "param_groups": list}`; neither is a tensor, so nothing is cloned and the "snapshot" aliases the live CUDA momentum tensors. Reproduced on torch 2.12: captured `exp_avg` 0.1355, live after 5 steps 2.1276, after `load_state_dict(snap)` 2.1276. So a restore rolls weights back to step 500 while keeping the step-730 Muon `mb` and Adam moments — ~20 misdirected steps, and the "restored last good state" print is false about half of what it claims.
- `sft_math.py:107` arms `good_opt = [None]*3` and only refreshes at `step % 200 == 0`, but `total_steps` is computed from the DDP-*sharded* shard, so real runs are 64-276 steps (`runs/sft_math.log` line 1: `step 10/186`). Step 200 is never reached: a NaN at step 170 reverts to the pre-SFT `--resume` checkpoint, the loop runs to the end, and `args.out` is saved unconditionally.
- `:143` uses bare `print`, not `runlog`, and the loss line at `:178` sits after the `continue`; `run_sft.sh` does not redirect torchrun stdout. `grep -rniE "nan|restor" runs/*.log` returns 0 across all 10 logs by construction.
**Fix:** `copy.deepcopy` the state_dict after moving tensors to CPU; `SAVE_INTERVAL = max(1, min(200, total_steps // 4))`; route the NaN print through `runlog`.

## 11. `dt_bias` initialized to zeros gives the KDA gate 0.11 per-token retention at init
`train.py:150`
**Defect:** `dt_bias = zeros(1024)` with `A_log = zeros`, `safe_gate=True`, `lower_bound=-5.0` (:173-174) makes the in-kernel gate `-5·sigmoid(exp(0)·(g+0))` ≈ -2.5.
**Failure:** measured with the real init (gate_proj std 0.02, RMSNorm'd input): `g_in` std 0.640, mean log-decay -2.500, mean retention **0.107** (p5 0.025 / p95 0.275) — the recurrent state of all 9 KDA layers is ~90% erased every token. fla's own layer uses `inv_softplus(dt)`, `dt ~ logU[1e-3, 0.1]`, giving retention 0.896. In `ckpt_k3-mla_2b_step2000.pt` `dt_bias` has climbed to mean -1.4/-2.7/-2.5 (retention 0.30-0.45) — after 2.26B tokens it is still below where fla's init starts.
**Fix:** `self.dt_bias.data.copy_(inv_softplus(dt))` with `dt ~ exp(U(log 1e-3, log 0.1))`, or a constant ≈ -3.

## 12. `--resume` runs a full fresh schedule, so the cosine ramps the LR back **up** past `total_steps`
`train.py:841-850, 893, 720-728`
**Defect:** `step = resume_step` (:893) but `total_steps` is recomputed from scratch and the epoch loop still runs all `Cfg.epochs`; `lr_mult` never clamps `progress`.
**Failure:** with the recorded 2.26B/6-GPU shape (`total_steps ≈ 3639`), `--resume ckpt.pt.step2000` starts at lr mult 0.80, reaches the 0.05 floor at 3639, then climbs back to **0.94** by the last step 5639 — the final `ckpt.pt` is saved at 94% of peak LR with no warning, because `0.5*(1+cos(πp))` is increasing for `p ∈ (1,2)`. Compounding: only `ck["model"]` is loaded (all three save sites store `{"model","cfg"}`), so Muon momentum and both Adam moments restart at zero; and the step is recovered by `re.search(r"step(\d+)")`, which returns 0 for per-epoch checkpoints named `ckpt.pt.ep1` and will match any `step` substring in the path.
**Fix:** clamp `progress` to `[0,1]` in `lr_mult`, and store `step` + optimizer state dicts in the checkpoint.

## 13. Strided DDP sharding gives ranks different step counts → LR divergence, then NCCL hang
`sft.py:64-65,100` and `sft_math.py:74-75,108`
**Defect:** `X = X[rank::world]` yields row counts differing by 1, and both `total_steps` and the inner loop bound are computed from the local shard with no cross-rank reduction.
**Failure:** 17,277 rows, 6 GPUs, batch 48 → ranks 0-2 get 2880 rows (60 iterations, `total_steps=60`), ranks 3-5 get 2879 (59). For 59 steps the two halves run *different* learning rates (`lr_mult(step, total)` and the wd ramp both divide by `total_steps`) on identical all-reduced gradients — DDP syncs grads, never weights, so the replicas drift and rank 0 saves its own copy. Then ranks 3-5 exit to `destroy_process_group()` while 0-2 enter a 60th backward → collective with 3 of 6 participants → watchdog timeout. Trigger rate over N ∈ [1000, 60000], world=6: 1.74% at batch 48, 2.60% at batch 32.
**Fix:** `n = min(len(X)//batch across ranks)` via one `all_reduce(MIN)` and truncate both the shard and `total_steps` to it.

## 14. `algorithms/rl.py` / `rl_arc.py` / `rl_ceval.py` are not runnable as written
Four independent defects in the older GRPO trio (superseded by `algorithms/rlvr*.py`, but still documented entry points in `README.md:20` and `algorithms/README.md:34-36`):
- **`rl.py:297-301`** — the `continue` on an empty `all_losses` is taken per-rank while the peers block in `dist.all_reduce(p.grad)` at :313. Because NCCL matches by call order, the first effect is worse than a hang: gradients computed at *different steps on different data* get summed and divided by `world`; the deadlock comes at the tail. Fix: all-reduce a `skip` flag and have every rank skip together.
- **`rl_arc.py:151` / `rl_ceval.py:151`** — `HybridLM(cfg).to(device).bfloat16()` then AdamW at `lr=2e-6` directly on bf16 params. bf16 ULP at |w|=0.02 is 1.22e-4, 61× the step; verified over 200 steps that weights at 0.02/0.05/0.1 come back bit-identical — ~96% of parameter mass is frozen and the run is a no-op. Introduced by d3f21e9, which added `.bfloat16()` to fix a generation dtype error. `rlvr_trainer.py:11-13` documents this exact hazard. Fix: fp32 master weights, or `autocast` instead of the cast.
- **`rl.py:138-144`** (same at `rl_arc.py:99`, `rl_ceval.py:99`) — the KL term is `log π − log π_ref` with `π_ref` under `no_grad`, so its gradient is the bare score function, expectation zero at θ = θ_old (which holds exactly: one `optimizer.step()` per rollout batch). `--beta 1.0` and `--beta 0` produce the same expected update; the anchor is cosmetic. Fix: k3 estimator `exp(r) − r − 1`, `r = ref_lp − lp`.
- **`rl_ceval.py:60`** — `\b([ABCD])\b` never matches next to a Chinese character (CJK is `\w`): `答案是A。` → None, `选A` → None, `答案：B` → B. Correct answers score 0 alongside wrong ones, so the reward trains formatting rather than correctness. Fix: `[ABCD]` with a non-letter lookaround, or `(?:答案|选)[^A-D]{0,3}([ABCD])`.

- **`tokenizer.json` (root, 0 bytes, tracked) vs `data/tokenizer.json` (2.85 MB, gitignored at `.gitignore:5`).** All 22 call sites read the gitignored one; nothing reads the tracked one.
